# Pages にスライド（deck）を載せる

図解・報告・提案などを **1 枚の HTML の deck** に組み、自分のサイト に投稿して URL を渡す。
位置づけは explain-page のスライド版。文章のページでも清書でもない。

**既定は「招待した人だけ」**（自分と、サイトに招待した人が Google アカウントでログインして開ける）。公開（ログインなしで誰でも読める）はユーザーが明示したときだけ。

**HTML そのものが原本。** ユーザーの git リポジトリ内に `<name>.html` を書き、それを投稿する。
Markdown からの変換は無い。投稿する HTML ＝ 原本ファイル ＋ 出典の札 1 行（札は機械が付ける）。

## 人／機械

| 誰が | 何を |
| :--- | :--- |
| **あなた（人の側）** | 目的と情報量に合う構図で HTML を組む。直す前後に同じ条件で全枚を撮り、意味と見た目を1枚ずつ目で確かめる。スラッグを決める。`check` と `publish` を打つ。止まったら `next` に従う。完了報告を書く |
| **機械** | 契約の検査・出典の札・投稿・片付け・報告の下書き |

検査・札の付与・投稿・片付けは自分で打たない。原本を投稿の途中で整形しない（古い雛形の差し替え・`<base>` の付与も禁止。黙って直すと取り込みが壊れる）。

`run.py` は**この手引きと同じフォルダの `scripts/` の中**にある（`<リポジトリ>/.claude/skills/explain-deck/scripts/run.py`）。

```bash
python3 <この手引きのフォルダ>/scripts/run.py check 原本.html
python3 <この手引きのフォルダ>/scripts/run.py publish 原本.html --slug decks/intro
```

パスは**そのまま書く**。引用符で囲むと、許可されているコマンドの型に当たらず確認を挟むことがある。

| 足すもの | いつ使うか |
| :--- | :--- |
| `--message "…"` | 投稿の履歴に残す 1 行（例: `スライド: decks/intro.html`） |
| `--public --yes-public` | **公開（ログインなしで誰でも読める）をユーザーが明示したときだけ。** 2 つそろって初めて効く |
| `--commit <40桁>` | 出し直すとき。依頼文のコミットとバイトが一致することを見る |
| `--dry-run` | 検査と写しまで見て、投稿も片付けもしない |

返るのは JSON。終了コードは **0 = 済んだ / 1 = 止まった / 2 = そもそも走れない**。

### スキル置き場の探し方

このスキルは、このリポジトリ（Pages の配布版）の `.claude/skills/` に入っている。
以下では、

- `<リポジトリ>` … このリポジトリの一番上のフォルダ（`bin/pages-publish.mjs` と `deployment.json` があるところ）
- `<スキル置き場>` … `<リポジトリ>/.claude/skills`（各スキルのフォルダと共通の `_shared/` が並んでいるところ）

と書く。スキルは別の仕事のフォルダからも呼ばれる（Claude Code のプラグイン、Cursor・Codex の近道）。
`<リポジトリ>` は、読んだ SKILL.md の**実体**から 3 つ上のフォルダ（`<リポジトリ>/.claude/skills/<スキル名>/SKILL.md`）。
近道越しに見えていても、近道の先で数える。最初に 1 回だけ、次で求めて確かめる。

```bash
python3 -c 'import pathlib,sys; p=pathlib.Path(sys.argv[1]).resolve().parents[3]; print(p if (p/"bin/pages-publish.mjs").is_file() and (p/".claude/skills/_shared/references/base.html").is_file() else "")' <読んだ SKILL.md のパス>
```

フォルダが 1 行出れば、それが `<リポジトリ>`。以降ずっとこれを使う。
コマンドは**いま開いているフォルダのまま**、`<リポジトリ>` を前に付けて打つ（`node <リポジトリ>/bin/pages-publish.mjs …` の形）。
作業ファイル（`page-out/` など）も、いま開いているフォルダに作る。
何も出なければ、配布物が欠けている。推測で探し回らず、そう伝えて止まる。

## 組む前に読むもの

### 自分の配色やロゴを使いたいとき

配布版には、あらかじめ決められたテーマは入っていない。見た目は下の「完成スタイル」から選ぶのが基本で、
自分の色やロゴを使いたいときは自分で設定する。

- 配色・書体・あしらいは、`<リポジトリ>/src/templates/deck-styles.json` の完成スタイルを 1 つ選んだうえで、基本設定（`data-deck-design`）で調整する。
  ユーザーが画面の「デザイン」から書き出した設定 JSON を渡したら、その配色・あしらいをそのまま基本設定に採用する
- ロゴを置くなら、ユーザーが用意した自分のロゴ画像を原稿と同じフォルダの `assets/` に置き、基本設定の `data-deck-logo` から相対パスで指す。
  1 資料につき 1 つ。画像の比率・透明な余白・元の色を保ち、描き直さない。他人や他社のロゴを勝手に使わない
- 右上にロゴ用の余白を残した枚に `data-dd-logo-safe="top-right"` を付ける。ロゴはこの目印のある枚だけに表示されるため、
  本文との重なりと実際の表示を確認する
- 投稿したあとは、ページを開いて画面の「デザイン」や「ロゴ」からも着せ替えられる。画面で保存した着せ替えの領域は原稿に書かない

`docs/guides/deck-design.md` にある「会社テーマ」の節と `pages-publish theme` / `themes` は、配布版では使えない。読み飛ばす。

### 共通の手引き

1. `<スキル置き場>/_shared/references/base.html` — 色の名前 `--ads-*` の正本
2. `<スキル置き場>/_shared/references/デザイン規則.md` — 通常ページの既定。スライドの色・構図・あしらいは下の専用手引きを優先する
3. 投稿の下ごしらえ — `<スキル置き場>/_shared/references/投稿の手順.md` の「投稿の下ごしらえ（前提確認）」（投稿先とログイン）
4. `python3 <この手引きのフォルダ>/scripts/run.py prepare` を実行する。返った `root` を以下の `<スライドの道具一式>` として使う（いつもこのリポジトリ＝`<リポジトリ>` が返る。外から取り寄せない）。画像の描画検査の道具もここで確かめる（下の「投稿の画質検査は省略しない」）。失敗したら返る `next` に従い、見本なしで作らない
5. `<スライドの道具一式>/docs/guides/deck-design.md` — **新しいスライドのデザインの正本。全文読む。** 同じ手引きが案内するプレゼン・提案・報告の3つの見本から、今回の用途に合うものを読む
6. `<スライドの道具一式>/src/templates/deck-styles.json` — 和文・英数字・配色・あしらいを組み合わせた完成スタイル。一つ選び、その `appearance` を基本設定の `document` に使う。個別の色や書体を初めから調整する前提にしない
7. `<スライドの道具一式>/docs/guides/deck-formats.md` — 文章、1〜N枚の画像、全グラフ、表、流れ・関係、コード・数式・動画・問いの形式台帳。必要な形式だけ選ぶ
8. `<スライドの道具一式>/tests/checks/fixtures/internal/example/deck-format-catalog.html` — 選んだ形式の実際の組み方。丸ごと写さず、該当する枚と共通部品を見る
9. `<スライドの道具一式>/src/templates/deck-design.html` — 配色・あしらい・構図・グラフの共通部品。`main` の直後へそのまま貼る
10. `<スライドの道具一式>/src/templates/deck.html` — 実行部。**1 字も変えずに** `</main>` の直後へ貼る（先頭の但し書きは貼らない。最初の `<style` から最後の `</script>` まで）

`投稿の手順.md` の Step 5「新しく作るとき」（`page-out/` に額縁をコピーする流れ）は**使わない**。
投稿の途中で原本を 1 バイトでも書き換えると、配信側が「ブラウザで直された」と誤検知する。
ふだん読むのは下ごしらえ・禁止事項・削除だけ。止まるときの `next` がそう指示したときも読む。

## 契約（書く形）

```html
<body data-deck>
  <main data-deck-slides>
    <section data-deck-slide>
      …本文…
      <aside data-deck-notes>…</aside>
    </section>
  </main>
  （src/templates/deck-design.html の共通部品）
  （src/templates/deck.html の実行部）
</body>
```

- `main` は body の直下。枚は `section`。入れ子にしない
- 動画は `controls playsinline preload="none"` と軽い `poster` を持つ標準の `video` で置く。自動再生しない。ブラウザ編集では「動画を追加」からMP4・WebMを送れる。投稿コマンドで送る素材は配布版では 1 つ 4MB まで。細部は専用手引きの「動画を使う」を参照する。
- 動画の字幕は `assets/` 内の `.vtt` を `<track>` から参照できる。音を出さずに操作を追えるようにし、文字起こしも本文に残す。字幕も通常の素材と同じ非公開の投稿経路を使う。
- ノートは任意。付けるなら**最後の子**。文章だけ（要素を入れない・入れ子にしない）
- 背景・強調色・あしらいは head の基本設定に書く。構図の CSS に色を焼き込まない。各枚には並べ替えても変えない目印を付ける（形は専用手引きが正本）
- 焦点を順に見せる枚は、head の原稿側の焦点設定へ手順を書く。枚・行・列・セル・系列・点・期間・画像領域・節点・辺を、位置や並び順ではなく安定した目印で指す
- 焦点の説明のうち読み手にも必要なものは公開の補足欄へ置く。発表者だけの話はノートへ置き、混ぜない。読む表示では各枚の後、印刷では全スライドの後に枚番号と題名つきの補足ページとして全部残す
- ロゴを原稿側で置くなら、1資料につき1つの非公開素材を相対パスで指し、全体設定と必要な枚だけの上書きを分ける。画像の比率・透明な余白・元の色を保つ
- 利用者が画面で保存する焦点・ロゴ・着せ替えの領域は書かない。原稿更新では安定した目印を維持し、見つからなくなった対象を別のものへ付け替えない
- 出典の札は人は書かない。機械が付ける。原本に札が既にあると検査が赤
- 新規の実行部は `<リポジトリ>/src/templates/deck.html` をそのまま貼る。既存資料は、登録済みの旧実行部（`<リポジトリ>/src/templates/deck-preview-compat.json`）と完全一致していればそのまま再投稿でき、`--base-version` を付けた送り直しでは公開する写しの中だけでいまの実行部へ差し替わる（原本は変わらない）。未登録・加工済みの実行部は検査で止まる。**検査を通すためだけに古い原稿の実行部を黙って貼り替えない**
- スクリプトはこのリポジトリが用意した部品（tailwind.js・lucide.js・mermaid.js・echarts.js と雛形の再生部品）だけが動く。独自の `<script>` と `onclick` などのイベント属性は書かない（投稿時に断られる。設定を書く `type="application/json"` の欄は専用手引きの形のまま使ってよい）
- 枚数・「はみ出し」などの字を DOM に足さない（索引と書き出しに混ざる）
- 印は Lucide の inline SVG。`<i data-lucide>` は使わない（実行部が外の CDN を取らない）
- 絵文字を使わない

## 内容から構図を決める

先に「誰に、何を判断・行動してほしいか」を整理し、各枚の結論と根拠を決める。
プレゼンは一文や大きな数・写真を主役にし、提案は比較・手順・図を、報告は要約・表・出典を組み合わせる。
1枚に主張は1つだが、根拠は複数あってよい。目次や扉を機械的に増やさない。

構図をそのまま写すことは必須ではない。**共通の文字・余白・配色の基準の中で組み合わせる。**
外側64px、12列・列間24px、本文20px以上。日本語の改行、長い数と単位、表の揃いまで整える。
収まらないときは内容整理・構図変更・分割で解決し、自動で文字を縮めない。

流れ・関係の図は、形式台帳から目的に合う形式を選び、新しい共通描画へ渡す。Mermaidの原文を正本とし、同じ図の別データや描画結果を書き足さない。名前と補足を分けるときは、原文中の明示改行を使う。HTMLの `pre` 内では改行タグを `&lt;br/&gt;` とエスケープする。

```html
<pre class="mermaid">flowchart LR
observe["観察する&lt;br/&gt;いま起きていることを見る"] edge-next@--&gt; try["試す&lt;br/&gt;小さく確かめる"]
</pre>
```

名前・補足・条件文は語句の切れ目で折り返し、句読点だけの行を作らない。条件の札を線に重ねず、矢印の行き先と条件の対応を読めるようにする。読む表示でも段階表示でも、1280×720の紙の大きさと図の配置を保つ。

完成スタイルは `<リポジトリ>/src/templates/deck-styles.json` の12種類から選ぶ。下地と複数の色、日本語と英数字の書体、見出しのあしらいを一組として使う。背景の淡い色と強調文字・図の濃さは描画側が調整する。利用者は「デザイン」の「完成スタイル」を選ぶだけでよく、個別の調整は「細かく調整」に置く。

全体と各枚の基本設定を持たせる。内容に意味のある写真を使ってよい。素材は既存の非公開保管庫と投稿の導線を使う。位置と文字サイズは原稿の構図を保つ。書体を意図して切り替えると改行は変わりうるため、切り替え後に全枚の収まりを確認する。色だけの変更・通常の強調・文字の入力中は、位置・寸法を変えない。

書体を含む新しい設定は、第3版の共通部品を埋め込んだ資料で使う。書体は読み込んでから適用・編集を始める。旧資料へ設定だけを足して表示を壊さない。保存された書体やあしらいを、原稿の取り込みで黙って落とさない。

ユーザーが書き出した設定を渡したら、その有効な配色・あしらいを新しい資料の基本設定に採用する。
設定の形、描画、優先順位、動きを減らす設定・印刷への対応は専用手引きが正本。
利用者の保存設定の領域は書かない。原稿を更新するときは、変わらない内容の各枚の目印を維持する。

ノートは話すことを**文章だけ**で書き、各枚の最後に置く。実行部は一字も変えず貼る。

## 画像と動画を用意する

決め方は 1 つだけ。**実物を見せる必要があるか。あるなら、止まった写真で足りるか、動く場面が要るか。**

| 要るもの | 用意の仕方 |
| :--- | :--- |
| 実在する物・場所・出来事の写真（製品、街並み、催しの様子など） | ユーザーが持っている写真を用意してもらうか、Openverse（無料・鍵なし）で探す。ユーザーが Serper の鍵を入れていれば Web 検索でも探せる（下の「写真を用意する」） |
| 実在しないもののイメージ（雰囲気の絵・挿絵） | 手元の AI に画像を作る道具があれば、それで作る（下の「絵を手元の AI で作る」）。無ければ図・印・文字で組む |
| 動く場面を見せないと伝わらないもの（実演・発表の一場面・自分で撮った動画の一節など） | YouTube などから短く切り出す（下の「動画を Web から取り寄せる」） |
| それ以外（考え方の図解・手順・関係・数・印・背景・雰囲気のイメージ） | 自分で作る。流れと関係は Mermaid、数はグラフの形式、印は Lucide の inline SVG、あしらいは基本設定と構図の CSS |

### 写真を用意する

配布版のサイトには、写真を探す検索の機能は入っていない（`pages-publish images search` / `images save` と、
`docs/guides/deck-design.md` にある画像検索の手順は使えない）。写真は手元から次のどれかで用意する。

| 方法 | 使えるとき | 出てくる写真 |
| :--- | :--- | :--- |
| ユーザーに用意してもらう | いつでも | ユーザーが撮った・作った写真 |
| **Openverse で探す（無料・既定）** | いつでも（鍵は要らない） | 自由に使ってよいと条件が付いた写真だけ（下の「Openverse で写真を探す」） |
| **Web 検索で探す（有料・任意）** | ユーザーが自分で Serper の鍵を取り、環境変数 `SERPER_API_KEY` に入れているときだけ | Google の画像検索の結果。**写真ごとに利用条件の確認が要る**（下の「Web 検索で写真を探す」） |

迷ったら Openverse から探す。Web 検索は、Openverse で見つからず、ユーザーが鍵を入れているときだけ使う（鍵を取るよう求めない）。

検索前ではなく**探す前に**、被写体・紙面上の幅と高さ・切り抜くか全体を見せるかを決めて伝える。
先に小さい画像を選び、あとから引き伸ばしてはいけない。

- 使えるのは、ユーザー自身が撮った・作った写真か、利用条件を確かめて使ってよいと分かっている写真だけ。
  WebSearch・WebFetch で画像を拾う、外のサイトから勝手に保存する、外部 URL を画像の参照へ書く、はしない
- 人の顔が主役の写真・他社のロゴ・報道写真・透かし入り素材は使わない。迷ったら別の表現にする
- 原稿は `index.html`、素材は同じフォルダの `assets/` に置き、相対パスで参照する。出典が要る写真は、その出典を枚に書く
- 配布版では素材 1 つ 4MB まで。大きすぎる写真は、必要な画素を保ったまま圧縮する（画素数を削りすぎると下の画質検査で止まる）
- 表示の縦横 2 倍の実画素が要る。切り抜きで枠の外に広がる部分も計算する。足りなければ、大きい原画像に替えるか構図を変える
- 原画像を原寸で見て、ぼけ・圧縮の乱れ・引き伸ばし・透かしがあるものは除く。寸法だけを大きく保存し直して検査を通さない
- 使わない素材は投稿するフォルダに残さない
- 写真が用意できないときは図や文字の構図へ切り替え、完了報告に 1 行書く。外のサイトから拾って埋め合わせない
- どの方法でも、探した写真は必ず `assets/` に保存して相対パスで指す（元のサイトの画像へ直接リンクしない。この仕組みは画像を非公開の置き場へ保存する）

#### Openverse で写真を探す（無料・鍵なし）

Openverse は、自由に使ってよい条件（クリエイティブ・コモンズなど）が付いた画像をまとめて探せる無料のサービス（WordPress の運営）。鍵は要らない。

1. 被写体・向き（横長が基本）を決めて、手元から 1 回探す。**条件は `cc0`・`pdm`・`by` の 3 つだけに絞る**（改変禁止・非営利限定・継承の条件が付いたものは出さない）。結果は保存してから読む

   ```bash
   curl -sS -A "surprise-pages-deck (explain-deck)" "https://api.openverse.org/v1/images/?q=<英語の検索語>&license=cc0,pdm,by&aspect_ratio=wide&size=large&page_size=20" -o path/to/deck-work/openverse.json
   ```

2. 返った `results` の `title`・`width`・`height`・`license`・`creator`・`provider` を見て候補を選び、`url` の画像を原稿のフォルダの `assets/` に保存する。
   保存したら Read で原寸を見て、ぼけ・透かし・人の顔が主役でないか・宣伝の文字が入っていないかを確かめる
3. 枚に出典を書く。結果の **`attribution` の文**（作者とライセンスが入っている）をその写真の枚の下に小さく載せ、
   元のページ（`foreign_landing_url`）とライセンスのページ（`license_url`）へリンクする。`cc0`・`pdm` でも出典は書く
4. 上の「写真を用意する」の決まり（大きさ・画素・顔・ロゴ・4MB）はそのまま守る

- 鍵なしの上限は 1 分に 20 回・1 日に 200 回。何度も探し直さない。429 が返ったら打ち直さずに止めて、ユーザーに伝える
- 写真の質は写真ごとにばらつく。良い候補が無ければ検索語を英語で 1〜2 回言い換え、それでも無ければ図や文字の構図にする

#### Web 検索で写真を探す（有料・鍵があるときだけ）

Google の画像検索の結果を Serper（Google の検索結果を返す有料の API）から取る。鍵は本人が https://serper.dev で取る
（無料の試しの分を使い切ったあとは有料）。鍵が無ければこの手順は使わない。

**Web の検索結果の画像には、それぞれ著作権がある。** 自由に使ってよいとは限らないので、写真ごとに元のページで利用条件を確かめ、許されている範囲でだけ使う。
初めて使う前に、この 1 文をユーザーに伝えて了解をもらう。

1. 鍵があるかだけを確かめる。**鍵の値は画面・出力・チャットに出さない**（`echo $SERPER_API_KEY` をしない）

   ```bash
   test -n "$SERPER_API_KEY" && echo "鍵あり" || echo "鍵なし"
   ```

2. 手元から 1 回探す。結果は保存してから読む

   ```bash
   curl -sS -X POST "https://google.serper.dev/images" -H "X-API-KEY: $SERPER_API_KEY" -H "content-type: application/json" -d '{"q":"<検索語>","gl":"jp","hl":"ja","safe":"active","num":20}' -o path/to/deck-work/serper.json
   ```

3. 返った `images` の `title`・`imageWidth`・`imageHeight`・`domain`・`link`（元のページ）を見て候補を選ぶ。
   **元のページ（`link`）を開いて利用条件を確かめ、使ってよいと分かったものだけ**、`imageUrl` の画像を `assets/` に保存する。
   条件が分からないもの・「転載禁止」とあるもの・写真素材サイトの有料素材は使わない
4. 枚に出典を書く。サイト名（`domain`）と元のページ（`link`）へのリンクを、その写真の枚の下に小さく載せる。元のページが求める表記があれば、それに従う
5. 上の「写真を用意する」の決まり（大きさ・画素・顔・ロゴ・4MB）はそのまま守る

- 1 回の検索ごとに料金がかかる。何度も探し直さない。429 や 401 が返ったら打ち直さずに止めて、ユーザーに伝える
- 使った写真ごとに、どの元のページで何の条件を確かめたかを完了報告に 1 行ずつ書く

### 絵を手元の AI で作る

雰囲気の絵や挿絵が要るときだけ。**API の鍵を新しく求めない。**

- いま使っている AI（Claude Code・Codex・Cursor など）に画像を作る道具があるときだけ使う。作れる道具が無ければ、図・印・文字で組む（無理に作らない）
- Claude Code は線の図（SVG）は描けるが、写真のような画像はそのままでは作れない。描けるのは図として Mermaid・Lucide・SVG で組む
- 作った画像は原稿のフォルダの `assets/` に保存し、相対パスで指す。実在の人物・他社のロゴ・実在の製品に見える絵は作らない
- 写真のような絵を本物の写真と誤解されないよう、ノートか枚の隅に「AI で作成したイメージ」と書く

### 投稿の画質検査は省略しない

投稿処理は、写しを作ったあと**画像送信より前**に同梱の検査を実行する。既存資料で画像追加後に保管される画像が変わった場合も、本文の送信前に再検査する。
この検査は、このリポジトリの `<リポジトリ>/bin/deck-image-check.mjs` を本物のブラウザ（Chromium）で動かして行う。初めて使うときは、
`<リポジトリ>` で次の 2 つを 1 回だけ打ってもらう（部品とブラウザを入れる。`prepare` が足りないと言ったときも同じ）。

```bash
pnpm install
pnpm exec playwright install chromium
```

投稿の前に自分で確かめたいときは、`node <リポジトリ>/bin/deck-image-check.mjs path/to/deck/index.html`（投稿済みの素材も見るときは `--page internal/<スラッグ>`）。
依存関係・ブラウザ・素材の読み込みを確認できなければ停止する。検査を飛ばす指定や別の投稿経路を作って迂回しない。
未対応の背景画像や図の中の写真も合格扱いしない。原寸目視は機械検査の代わりではなく、ぼけや圧縮の乱れを判断するために併用する。

`check` はHTMLの形の確認、`publish` の画質検査は描画の確認である。`--dry-run` は通信せず、画質は「未確認」と返す。dry-runだけで画質検査済みと報告してはいけない。

### 動画を Web から取り寄せる

動く場面を見せないと伝わらないときだけ使う（写真や図で足りるなら、そちらにする）。
**手元の yt-dlp で取り寄せ、FFmpeg で短く切り出す**。サーバーも鍵も使わない。

動画の置き方は 2 通りある。

| 置き方 | 1 本の上限 | 使うとき |
| :--- | :--- | :--- |
| 原稿の `assets/` に置いて `publish` する | 4MB | 10 秒前後の短い場面 |
| 投稿したあと、編集画面の「挿入 → 動画」から MP4・WebM を選ぶ | 100MB | 長めの動画。2MB ずつ送られ、サーバーでは変換しない（静止画はブラウザが最初の場面から作る） |

どちらでも、サーバーでの変換（軽量化）はしない。**先に手元の FFmpeg で小さくしてから**置く（下のコマンドの `-crf 23` と 720p で十分）。

**どの動画を使ってよいか**

- 自分のチャンネルの動画と、権利者・制作元の公式チャンネルを優先する。公開されていることと、使ってよいことを混同しない。使ってよいか分からなければ使わない
- 説明に要る短い区間だけを切り出し、何を見せるためかをノートに書く。チャンネルや再生リストをまとめて取らない
- ログイン・Cookie・地域制限・DRM（コピー防止）を回避しない。有料配信サービスの本体からは取らない

**道具をそろえる**

```bash
yt-dlp --version; ffmpeg -version | head -1; ffprobe -version | head -1; deno --version | head -1
```

- 無いものがあれば、入れてよいかをユーザーに 1 回聞いてから 入れる（Mac は `brew install yt-dlp ffmpeg deno`。Windows は各道具の公式の案内に従う）
- **yt-dlp は古いと YouTube に 403 で断られる**（2026-10-05 の実測: Homebrew の 2026.06.09 は 403、公式の 2026.08.19 は成功）。
  `brew outdated yt-dlp` で遅れていたら、ユーザーに伝えて `brew upgrade yt-dlp` してから試す。403 をすべて版のせいと決めつけない。429 なら打ち直さずに止める

**取り寄せて切り出す**

原本は**原稿のフォルダの外**（例: `path/to/deck-work/originals`）に置く。`assets/` に置くと 100MB 近い原本が一緒に上がる。
区間だけを取る指定（`--download-sections`）は 403 になることがあるので、原本をまるごと 1 回取ってから手元で切る。

```bash
yt-dlp --ignore-config --no-playlist --no-overwrites -f 'bv*[height<=720]+ba/b[height<=720]' -S 'res,vcodec:h264,acodec:aac' --merge-output-format mkv -P path/to/deck-work/originals -o '%(id)s.%(ext)s' -- 'https://www.youtube.com/watch?v=<動画のID>'
ffmpeg -n -ss 60 -i path/to/deck-work/originals/<動画のID>.mkv -t 10 -map 0:v:0 -map '0:a:0?' -vf "scale='min(1280,iw)':-2" -c:v libx264 -preset medium -crf 23 -pix_fmt yuv420p -c:a aac -b:a 128k -movflags +faststart path/to/deck/assets/<名前>-0060-0070.mp4
ffmpeg -n -ss 1 -i path/to/deck/assets/<名前>-0060-0070.mp4 -frames:v 1 -q:v 3 path/to/deck/assets/<名前>-0060-0070-poster.jpg
ffprobe -v error -show_entries stream=codec_type,codec_name,width,height:format=duration -of compact path/to/deck/assets/<名前>-0060-0070.mp4
```

- URL は必ず `--` の後ろに引用符で囲んで渡す。ファイル名は英小文字・数字・`-` で、元の秒が分かる形にする
- 検査で映像（h264）と音声（aac）・尺がそろっているかを見る。原稿から置くときは 1 本 4MB まで（10 秒の 720p で約 1MB）。それより長い動画は、投稿後に編集画面の「挿入 → 動画」から置く（100MB まで）。プレビュー画像を Read で開き、見せたい場面かを確かめる
- 置き方は「契約（書く形）」の動画の決まりどおり（`controls playsinline preload="none"` と `poster`、相対パスの `src`、自動再生しない）
- 枚に「出典: <投稿元>（YouTube）1:00〜1:10」を書き、ノートに元の URL・使った秒・見せる意図を書く
- 投稿が済んだら原本を片付ける。動画を git に入れない

## 組んだあと

1. ユーザーの git に `<name>.html` を書く（英小文字・数字・`-` `_` `.` `/`）。**ここに書いたファイルが原本**
2. `<スライドの道具一式>/docs/guides/deck-design.md` の「出す前の確認」を省略せず行う。書体・画像・グラフ・図の描画完了を待ち、焦点を解除してから、直す前の全枚を1280×720原寸と幅390pxで1枚ずつ撮る。幅390pxはChromium系とSafari/WebKit系の両方で撮る。順番が分かる一覧も作る。撮った枚の目印とファイル名を突き合わせ、抜け・重複・直前の枚の写り込みがないことを確認する。検査画像は投稿する素材の隣に置かない
3. 各枚について「意味・視線・主従・余白・文字」を記録し、原寸では見出しの折返し・行間・本文との距離・端の揃い・画像4辺・ロゴ端距離を1px単位で確認する。図表内のラベルは画面上の実寸も測る。幅390pxでは第一視線と読める順を実際の大きさで見る。Safari/WebKitでは図の文字が横帯だけにならず、文字の表示領域が内容より小さくないことを全図で確かめる。全体では構図の連続、色の役割、ロゴの強さを確かめる。画像取得エラー0件や枚の外へのはみ出し0件だけで合格にしない
4. 共通する欠陥は共通部品で、内容固有の欠陥はその枚で直す。同じ条件・順番・名前で全枚を再撮影し、直す前後を比べる。交差0や数値範囲内でも、第一視線、ラベル、余白、折返しに問題があれば直す。数値が合格でも同じ状態の画像が崩れて見える、または原寸と小画面の値が逆転するなど、数値と画像が矛盾したら不合格に戻して測る対象・縮尺・描画待ちを直す。重大な指摘が0件になるまで繰り返す。機械検査は目視の代わりにしない
5. 配色とあしらいを変えても文字が動かないこと、発表・小画面・印刷での見え方も確認する。段階表示は原寸で「全体→注目点→全体」を実際に操作し、前後移動・一覧・終了をキーと画面の操作から確かめる。注目点と条件文が対応し、操作中も紙の大きさ・文字・図の配置が変わらないことを見る
6. `check` が緑なら `publish`。未コミットでも出せる（札は「作業中の内容」）。コミットしてから出すと札に commit が載る
7. **出したあと、サイトの上で描画を検査して直す**（下の「投稿したあとの描画の検査」）。手元で撮った画像と、サイトで実際に描かれた結果がずれることがあるため
8. 公開なら、完了報告に「ノートは画面に出ない」と 1 行伝える。書かせ方は変えない

### 投稿したあとの描画の検査

配布物には、手元の AI から資料を読み・直すための道具（`<リポジトリ>/bin/pages-agent.mjs`。AI からは `surprise-pages` という名前で見える）が入っている。
サーバーでは何も動かさず、検査は手元のブラウザ（Chromium）で行う。

- まだ登録していなければ、ユーザーに 1 回だけ `node <リポジトリ>/bin/install-pages-agent.mjs` を打ってもらう（Claude Code と Codex に登録される。Cursor には登録されない）。
  登録したら新しい会話から使える。登録できない・使えない AI では、この節を飛ばして完了報告に「描画の検査は未実施」と 1 行書く
- 使い方（どれも投稿された資料の URL を渡す）

| 順 | 道具 | すること |
| :--- | :--- | :--- |
| 1 | `page_read`（`view: "overview"` → `view: "layout"`） | サイトで描いたときの、枚ごとの要素の位置・大きさ・書体を読む。1280×720 の枠の外へ出た要素や、重なった要素を探す |
| 2 | `page_prepare` | 問題のある枚だけを直す案を作る（内容は変えない。内容を変えるなら原稿を直して出し直す） |
| 3 | `page_verify` | 直した枚だけを手元のブラウザで描き、はみ出し・重なりを機械で検査する。返った画像を Read で見る |
| 4 | `page_apply` | 確かめた案を保存する |

- はみ出し・重なりが 0 になるまで 2〜4 を繰り返す。直せないときは、文字を縮めずに内容を整理するか枚を分ける
- 道具で直した分は手元の原稿に入らない。あとで原稿から出し直すときは、先に `run.py read` で今の本文と比べる（下の「すでにあるページを出し直すとき」）

鍵（ログインの控え）の中身を、画面・出力・チャットに出さない。

## 止まったとき

**`error` を自分で解釈しない。`next` に書いてあることを 1 つやる。** 雛形の差分を黙って直さない。

| `stage` | 何が起きたか | やること |
| :--- | :--- | :--- |
| `preflight` | 投稿コマンドが用意できない／まだログインしていない | `next` のとおり。ログインは人のパソコンでブラウザを開く話なので、URL を渡して待つ |
| `check` | 契約に合わない | 原本を直してから `check` を打ち直す。雛形が違うときは原本を直してコミットしてから |
| `update` | 版の不足・競合・画像追加の失敗 | `next` に従う。競合時は最新版と変更案を再比較し、版番号だけを取り替えない |
| `publish` | 投稿が通らなかった | 出力を確認する。競合時は最新版と変更案を再比較する。原本は触っていない |

## すでにあるページを出し直すとき

手元のチャットで「このスライドを最新にして」「このスライドを直して」と言われたときの手順。

### 画像付きの原稿を投稿し直す

投稿スクリプト自身が現在の版の照合・画像追加・本文更新を順番に実行する。**先に現在の本文と完全な版番号を読み、今回の変更案と比較する。** 既存の本文・配置を消す変更を採用しない。

```bash
python3 <スキル置き場>/explain-deck/scripts/run.py read --slug decks/intro
# 返った html と変更案を比較し、versionId（40桁）を控える
python3 <スキル置き場>/explain-deck/scripts/run.py publish path/to/index.html --slug decks/intro --base-version <比較したversionId>
```

- 新規投稿では `--base-version` は不要。既存ページでは省略すると画像を送る前に止まる。
- 追加画像は `index.html` と同じ場所の `assets/` に置き、画像属性（src / srcset / poster など）または CSS の `url(...)` から相対パスで参照する。既存更新で追加できるのは PNG・JPEG・WebP・GIF・AVIF。配布版では素材 1 つ 4MB 以下に収める。SVG・動画・字幕などの新規追加はこの更新経路では停止する。既存の保管済み素材は手元へ写さず、その参照を残す。
- 既存ページでは一般投稿の素材窓口へ送らず、編集用の画像追加を使う。返った保存先で**投稿用の写しの参照だけ**を差し替え、比較した版を付けて本文を更新する。原本は変えず、保管済み素材の削除一覧も送らない。
- 画像追加前・本文送信前・サーバーでの保存時に競合を確認する。途中で他の人が更新したら停止する。**最新版の番号だけを差し替えて再送しない。** 最新の本文と変更案を再比較し、取り込む内容を決め直す。送信済みの画像があっても、競合時に本文や以前の画像は上書きしない。
- `--dry-run` は原稿と投稿用の写しの検査だけ。通信しないため、現在の版・編集権限・画像追加の成否は実投稿時に確認する。

投稿先と鍵は、投稿コマンドの設定（`node <リポジトリ>/bin/pages-publish.mjs config --json` で見える自分のサイトとログインの控え）から取る。

ページの削除は `<スキル置き場>/_shared/references/投稿の手順.md` の「ページの削除」。
投稿まわりの禁止事項もそこの「守ること（禁止事項）」が正本。
