# 投稿の手順

この文書は、自分のサイト に投稿するすべてのスキル（呼び出し側）から読まれる共通の手順書。ページの中身をどう作るかはスキルごとに違うが、
**作り終えてから投稿して URL を渡すまでの流れは共通**で、ここに書いてあるとおりに進める。

スキルはこのリポジトリ（Pages の配布版）の `.claude/skills/` に入っている。以下では、

- `<リポジトリ>` … このリポジトリの一番上のフォルダ（`bin/pages-publish.mjs` と `deployment.json` があるところ）
- `<スキル置き場>` … `<リポジトリ>/.claude/skills`（各スキルのフォルダと共通の `_shared/` が並んでいるところ）

と書く。`<リポジトリ>` の求め方は、各スキルの手引きの「スキル置き場の探し方」。
コマンドは**いま開いているフォルダのまま**、`<リポジトリ>` を前に付けて打つ（`node <リポジトリ>/bin/pages-publish.mjs …` の形）。
投稿の道具は Node.js で動くので、Mac でも Windows でも同じ書き方で使える。
`bin/pages-publish`（拡張子の無いほう）は使わない。

## 投稿の下ごしらえ（前提確認）

2 つ確認する。

**1. 投稿の道具と投稿先がそろっているか**

投稿の道具はこのリポジトリに入っている。別の場所から取ってきたり、`git clone` したりしない。
投稿先（自分のサイトの URL）と、鍵の控えの置き場所は次で分かる。鍵の中身は表示されない。

```bash
node <リポジトリ>/bin/pages-publish.mjs config --json
```

- `origin` が自分のサイトの URL になっていれば、投稿先は設定済み
- 「先に … personal.mjs configure で投稿先を設定してください」と出たら、投稿先が未設定。
  ユーザーに次を打ってもらう（自分のサイトの URL を聞かれる）

```bash
node <リポジトリ>/scripts/setup/personal.mjs configure
```

- `<リポジトリ>/bin/pages-publish.mjs` そのものが無いなら、配布物が欠けている。
  推測で探し回らず、そう伝えて止まる

投稿先は自分のサイトだけ。ほかの人のサイトや、配布元のサイトへは投稿しない（道具も断る）。

**2. ログインできているか**

投稿には、自分のサイトの持ち主の Google アカウントでのログインが 1 回だけ要る。
済んでいるかどうかは、上の `config --json` に出る `credentialFile` のファイルがあるかで分かる（**中身は開かない**）。

```bash
ls -l <credentialFile に出たパス>
```

未ログインでも Step 5（ファイル作成）までは進めてよい。投稿の直前にもう一度案内する。

ログインは、ユーザーに次を打ってもらう（**このスキルからは実行しない**。ブラウザが開くため）。

```bash
node <リポジトリ>/bin/pages-publish.mjs login
```

ブラウザが開くので、サイトを設置したときの本人の Google アカウントで許可するだけで終わる。一度済ませれば、
そのパソコンでは次から聞かれない。ブラウザが開かなければ、画面に出た URL を本人が自分のブラウザで開く。

- **エージェントがブラウザを開かない。** 開くのはユーザー本人
- **控えがあるのにログインし直さない。** あるかどうかだけ見る。中身は見ない
- **鍵の中身を画面やチャットに出さない・貼らせない**
- クラウドの作業環境から投稿するときは、先に `login --remote` で名乗りを用意する（README の第 4-4 章）

Python で動く道具（清書・読む・スライドのスクリプト）は `python3` で呼ぶ。Windows で `python3` が見つからないときは、
`python` か `py` で同じものを呼ぶ。

## Step 5: ファイル作成

**最初に分ける。新しく作るのか、すでにあるページを直すのか。**
直すなら、この下の「すでにあるページを直すとき」へ進み、1〜7 は飛ばす。

### すでにあるページを直すとき

**スライド（deck）の画像付き更新は explain-deck の「画像付きの原稿を投稿し直す」へ進む。** `read --slug` で現在の本文と版を取得して比較し、`publish --base-version` に同じ版を渡す。画像追加は編集用の入口、本文は比較した版を指定して更新する。既存スライドに通常の `node <リポジトリ>/bin/pages-publish.mjs --dir` を使わない。記事の更新は以下の手順。

**白紙から書き直さない。HTML 全文も読まない。** コメントを見て直すなら、先に読むスキルの `revise`。

```bash
python3 <スキル置き場>/read-page/scripts/run.py revise https://自分のサイト/internal/diagrams/api-basics
```

`revise` が種類を見分ける。

- **清書**（末尾に出所の切手がある）→ `page-out/原本.md` を直す。HTML は触らない。直し終わったら清書のスキルで同じスラッグへ出し直す
- **図解**（切手が無い）→ 文脈は `page-out/本文.md`。直すのは `snippets/` の断片を手がかりにした `index.html` の該当箇所だけ。`本文.md` は投稿しない。`index.html` を最初から読まない

`node <リポジトリ>/bin/pages-publish.mjs get` や `read --out` で HTML だけ戻したときも、**戻した HTML を全文 Read しない。** 直す起点は `revise`。

**なぜ戻すのか。** 投稿が終わると手元の作業フォルダはゴミ箱へ入れる決まり（この章の
「投稿できたら、手元の作業ファイルをゴミ箱へ」）なので、次に直すときには手元が空に
なっている。そこで書き直すと、直したいのは 1 行なのに残りが全部別物になる。前の版に
あった数字も、順序も、注意書きも、書いた本人以外には戻せない。正本はサイトの保管庫にあるので、
そこから戻す。

**ゴミ箱を掘り返さない。** macOS はゴミ箱の中を読ませないので、そもそも取り出せない
（理由は同じ章の最後にある）。別のパソコンには残っていないし、
ブラウザの画面から後で直した版も入っていない。

| 足すもの | いつ使うか |
| --- | --- |
| `--out <フォルダ>` | 出す先を変える（既定は `page-out`） |
| `--public` | 公開ページ（`/public/...`）を直すとき |
| `--version <目印>` | 過去の版を戻す（履歴の画面に出ている 7 桁でよい） |

すでに `page-out/index.html` や `原本.md` / `本文.md` があると断られる。前回の本文と
混ざらないようにするため。片付けてから、もう一度打つ。

**戻ってくる画像や動画は保管庫に置いたまま**なので、手元で開くと絵は出ない。
**割れて見えても直さないこと**——そのまま投稿し直せば元どおり出る（絵の場所は
配信のときに支えられている）。新しい画像を足すときだけ、`page-out/` に置いて相対パスで
参照する。

### 新しく作るとき

1. 作業用のフォルダを `<リポジトリ>` に `page-out/` という名前で 1 つ作る。**名前を変えない**（投稿のあとの片付けが、この名前を前提にしている）
2. トピックに関連する短い英小文字のスラッグを決める（例: `api-basics`、`rls-flow`、`2026-08-09-kickoff`）
3. `<スキル置き場>/_shared/references/base.html` を `page-out/index.html` にコピーする
4. コピーしたファイル内の差し込み位置をすべて置き換える
   - `<!-- TITLE -->` → ページの見出し（**そのまま自分のサイトの一覧に並ぶ**）
   - `<!-- DESCRIPTION -->` → 内容を要約した 1 文
   - この 2 つはチャットや SNS に貼ったときのカードの文言にもなる。**残り（カードの絵・タブの印・宛先）は
     配信側が差し込む**ので、`og:image` や `rel="icon"` を書き足さない（宛先を知っているのはサーバーだけ）
   - `<!-- CONTENT_START -->` 〜 `<!-- CONTENT_END -->` → 本文（呼び出し側の手順で作ったもの）
5. 画像を使う場合は**同じフォルダに置いて相対パスで参照する**（`<img src="shot.png">`）。理由は「守ること」の章にある。
   配布版では、画像・動画などの素材は **1 つ 4MB まで**。大きいものは縮めてから置く
6. ファイル名とスラッグに使えるのは**英小文字・数字・`-` `_` `.` `/` だけ**。日本語や空白が入ると投稿時にエラーで止まる
7. **投稿前に見直す** — 書いた HTML を見返し、次を確かめる。1 つでも当てはまったら直してから投稿する
   - **色**: 生の色名（`slate` `blue` `white` など）を**絵の外**に書いていないか／絵の中に名前（`ads-*`）を混ぜていないか／並列に並ぶ項目を 1 つずつ違う色にしていないか／同じ色が 2 つの意味で使われていないか
   - **絵の印**: 実在の画面を模したミニ UI の器に `data-ads-figure="light"` か `"dark"` を付けたか（絵の地色で決める）
   - **線と箱**: 区切りの横線を余白で代えられないか／箱の中に同じ色の箱が入っていないか／押せない要素が押せる見た目になっていないか／PDF や先頭へ戻るを本文に複製していないか（どちらも額縁が持つ。PDF はページの頭にあり本文と一緒に流れていく。先頭へ戻るは画面の左下に浮いていて、配信側が右下に出す道具とは別。なお公開すると、PDF ボタンは配信側の書き出しメニュー（アイコンだけ。コピー・ファイルに保存・PDF）に置き換わる。手元で開いたときと見た目が違うのはそのため）
   - **貼り付く要素**: 本文に `sticky` や `fixed` を置いていないか（額縁の先頭へ戻るが左下に、配信側の道具が右下に浮いているので、席を取り合って重なる）
   - **文字サイズ**: 同じ役割の要素でサイズが揃っているか／下位の要素が上位より大きくなっていないか
   - **図**: `<pre class="mermaid">` を置いたなら、貼る一式（script 2 本と style 1 枚）が `</head>` の直前にあるか（`<script>` だけ貼って `<style>` を落としていないか。無いと図の文が文字のまま出る／狭い画面で図が潰れる）／図の中で色を指定していないか／図を `bg-ads-surface` の箱に入れていないか
   - 詳しくは `<スキル置き場>/_shared/references/デザイン規則.md` の「色の使い方」「線と箱の使い方」「文字サイズの決め方」を読み返すこと

ブラウザで開くのは Step 6 の投稿後にする。

### 図（流れ図・順序図・状態遷移図・日程）を入れるとき

図は**文字で書く**。絵を貼るのではないので、直すときは描き直さずに文を直せる。
いつ図の文で書き、いつ Tailwind で組むかの分かれ目は、呼び出し側のスキルの手引きにある。
**組み方を決めてからここへ来ること。**

図を 1 つでも置くなら、**額縁の `</head>` の直前に「貼る一式」を足す**。

```text
<リポジトリ>/src/templates/mermaid.html
```

このファイルを Read し、**最初の `<script` から最後の `</script>` まで**をひとかたまりで貼る
（`<script>` 2 本と、その間の `<style>` 1 枚）。先頭の但し書き（`<!--` 〜 `-->`）と、
末尾の見本（`<pre class="mermaid">` **すべて**）は貼らない。見本は書き方を示すために
置いてあるだけで、枚数は増えることがある。**数で覚えず、`</script>` から後ろは全部**と覚える。

- **1 文字も変えない。** コメントも字下げも含めてそのまま写す。ここが色・置き方・絵記号の
  正本で、額縁が持っている色の名前（`--ads-*`）を読む作りになっている。
  **貼るだけでページの色になじむ**
- **`<style>` を落とさない。** あれが「幅が足りないときに縮めず横へ送る」を持っている。
  落とすと、スマホで図が 0.44 倍まで縮んで字が 5px になる（広い画面では何も起きないので、
  手元で見ている限り気づけない）
- **色を書き足さない。** 図の中で `style` や `classDef` に色を指定しない（額縁から入る）。
  1 つだけ目立たせたいときは `classDef accent stroke-width:2px` のように**太さで**示す
- **図を置かないページには足さない。** 図の道具は大きいので、使わないページでは読み込ませない

図を出したい場所には `<pre class="mermaid">` を置き、中に図の文を書く。

```html
<pre class="mermaid">
sequenceDiagram
  actor 読む人
  participant アプリ
  participant サーバー
  読む人->>アプリ: 開く
  アプリ->>サーバー: 中身をください
  サーバー-->>アプリ: 中身
</pre>
```

- **`actor` は人、`participant` は仕組み。** 人は絵記号で、仕組みは箱で出る。
  出てくるのが全部システムなら `actor` を使わない
- **図に面を敷かない。** `<pre class="mermaid">` を `bg-ads-surface` の箱に入れないこと。
  図の箱も矢印の札の下敷きも**紙の色**なので、面の上に置くと白い四角がいくつも浮いて出る。
  本文からの切り出しは、面ではなく見出しと余白で行う
  （手で組んだ図に面を敷いてよいのは、あちらが自前の輪郭を持たないため）
- **図を横幅いっぱいに使わせる。** 図を囲む要素に左右の余白を足さない。
  余白を足したぶんだけ、狭い画面で横へ送る距離が伸びる。日程は**段の幅に合わせて自分で詰まる**
  ので、囲む要素を狭くすると帯と日付が並ぶところだけが狭くなる
- **状態遷移図で、戻れる先が 2 つ以上に枝分かれするときは `direction LR` と書く。**
  既定の縦だと、枝分かれの札が全部おなじ高さの 1 段に並び、隣り合う 2 つが別の組の札になって
  読めなくなる。行き止まりは「出ていく矢印が 1 本も無い箱」で示す
- **日程（`gantt`）の `section` の名前は短くする。** 区間名は図の左に列で出て、
  列の幅は**いちばん長い名前に合わせて伸びる**（入る幅を取るので、はみ出して帯に重なることは
  無い）。伸びたぶんは帯と日付が並ぶところが詰まって埋め合わされるが、詰めきれない狭い画面では
  そのぶん横へ送る距離が伸びる。名前は「下ごしらえ」「仕上げ」くらいの短さで置き、
  説明は帯（作業）の名前のほうに書く
- 貼り忘れると、図の文が**そのまま文字として画面に出る**。投稿前の見直しで必ず見る

## Step 6: 投稿

投稿は必ず `node <リポジトリ>/bin/pages-publish.mjs` を使う。ここを迂回して保管庫やデータベースへ直接書き込まない。

```bash
# 画像つき・フォルダごと（index.html が本体）。基本はこちら
node <リポジトリ>/bin/pages-publish.mjs --dir page-out --slug diagrams/api-basics

# 文字だけの 1 枚もの
node <リポジトリ>/bin/pages-publish.mjs --file page-out/index.html --slug reports/2026-08-09-kickoff
```

`--slug` がそのまま URL になる。日付や案件名で階層を切ると後から探しやすい。
同じスラッグへ投稿し直すと、そのページの新しい版になる（URL は変わらない）。

**既定は「招待した人だけ」。** 付けるものは何も無い。開けるのは、サイトの持ち主（自分）と、
サイトに招待した人だけ（どちらも Google アカウントでログインして開く）。

**公開（ログインなしで誰でも読める）は、ユーザーが明示的に指示したときだけ。** そのときだけ `--public` を付ける。

```bash
node <リポジトリ>/bin/pages-publish.mjs --file page-out/index.html --slug onboarding --public
```

確認を聞かれるので、**ユーザーに見せてから答える**。対話できない環境でだけ `--yes` を付けてよい。

`--public` と `--delete` は確認プロンプトが出る。対話できない環境では `--yes` が要る。
**勝手に `--yes` を付けて公開・削除しない。**

**迷ったら「招待した人だけ」で投稿してよい。** あとからユーザー自身が画面で公開に切り替えられる
（ページを開いて右下の「共有範囲」から）。そのとき **URL は変わらない**——
いまの URL はそのまま生き続け、公開用の URL が 1 本増えるだけ。だから
「公開するかもしれないから最初から `--public` で」と先回りしなくてよい。
逆に `--public` で投稿してしまうと、あとから「招待した人だけ」には戻せない（投稿し直しになる）。

### 投稿できたら、手元の作業ファイルをゴミ箱へ

**投稿が成功した直後に、ここまでを 1 つの手順として済ませる。** 別の作業として後回しにしない。

Mac では次の 1 行。

```bash
mv ./page-out ~/.Trash/"page-out-$(date +%Y%m%d-%H%M%S)"
```

時刻を付けるのは、ゴミ箱に同じ名前が既にあると**中へ潜り込んでしまう**ため（上書きにもならず、
入れ子が増えていく）。

Windows など、ゴミ箱の場所が違う環境では自分で消さない。ユーザーに「`page-out` フォルダを
ゴミ箱へ移してください」と頼む（エクスプローラーで右クリック → 削除なら、ゴミ箱に入る）。

清書のスキルでは、照合のために本文だけを取り出した一時ファイルも作っている。あれも一緒に入れる（Mac の場合）。

```bash
[ -f 本文.html ] && mv 本文.html ~/.Trash/"本文-$(date +%Y%m%d-%H%M%S).html"
```

**なぜ片付けるか。** `page-out/` は投稿するためだけに組み立てた控えで、**正本はサイトの保管庫にある**
（投稿すると版として積まれる）。手元に残すと 2 つ困る。次に同じスキルを動かしたときに前回の
`index.html` が残っていて、どちらが今のものか分からなくなる。そしてリポジトリの中に
身に覚えのない未コミットのファイルとしてずっと居座る。

**消さずにゴミ箱に入れる。** すぐ戻せる状態を残すため（取り返しのつかない消し方をしない）。

**ただし「あの HTML をもう一度」は、ゴミ箱からではなく取り寄せる**（Step 5 の
「すでにあるページを直すとき」）。ゴミ箱の中は読めないうえ、正本は保管庫にあって
そちらのほうが新しい（ブラウザの画面から後で直しているかもしれない）。

**ゴミ箱へ入れてよいのは、このスキルが作ったものだけ。**

| 入れる | 入れない |
| --- | --- |
| `page-out/`（作業用のフォルダまるごと） | ユーザーが渡した原本（`.md` など） |
| `本文.html`（照合のための一時ファイル） | ユーザーが自分で用意した画像などの元ファイル |
| | ユーザーが置き場所を指定して作らせたファイル |

見分け方は「**自分が作ったか**」だけ。ユーザーが前から持っていたものには、いかなる理由でも触らない。
迷ったら入れない（残っているごみは次に片付けられるが、間違って入れたものは気づかれない）。

**投稿に失敗したときは片付けない。** 直してもう一度投稿するのに要る。片付けるのは、
投稿コマンドが URL を返したあとだけ。

**片付いたかは「元の場所が空になったか」で見る。ゴミ箱の中を覗こうとしない。**
macOS はゴミ箱の中を読ませない（`ls ~/.Trash` は `Operation not permitted` で断られる。
ターミナルにフルディスクアクセスを与えていない限り、これが正常）。書き込みは通るので
移動そのものは成功しているのに、覗いて断られたのを「失敗した」と読み違えると、
**もっと強い消し方（`rm -rf`）に手を伸ばす**——そちらは戻せない。断られても何もしないこと。

### エラーが出た場合

エラーメッセージをそのまま見せず、**何が起きていて何をすれば解決するか**を専門用語を避けて説明する。

- **投稿先が設定されていない** — 「投稿の下ごしらえ（前提確認）」の 1 番の `configure` をユーザーに案内する（**このスキルからは実行しない**）
- **まだ投稿できません / このパソコンからは投稿できなくなっています** — ログインが済んでいない、または切れている。「投稿の下ごしらえ（前提確認）」の 2 番の `login` をユーザーに案内する（**このスキルからは実行しない**）
- **サイトにつながらない** — 自分のサイトが止まっているか、URL が違う。ブラウザで自分のサイトを開けるか本人に確かめてもらう。設置の状態は README の第 3-11 章の診断（`node <リポジトリ>/scripts/setup/personal.mjs doctor`）で確かめられる
- **スラッグが不正** — 日本語・空白・大文字が入っている。英小文字と `-` に直す
- **HTML や素材が大きすぎる** — 画像を埋め込んでいるか、素材が 4MB を超えている。画像はフォルダに出して `--dir` で投稿し、大きい素材は縮めてから置き直す

## Step 7: 完了報告

```
完成・投稿完了: 【ページの見出し】

（内容を 1〜2 文で要約）

URL（招待した人だけ）:
【投稿コマンドが出した URL】

主なポイント:
- （3〜5 個）

このページを消したいとき:
チャット欄で「このページを消して」と伝えてください。

手元の作業ファイル: ゴミ箱に入れました
```

最後の 1 行は**片付けを済ませてから書く**。書いてあるのに残っている、が起きないようにする
（報告に出しておくと、やり忘れたときに自分でも気づける）。Windows などでユーザーに片付けを頼んだときは、
「`page-out` をゴミ箱へ移してください」と書く。

URL は投稿コマンドが出力したものをそのまま使う。**加工しない。**
この URL を開けるのは、自分と、サイトに招待した人だけ（Google アカウントでログインして開く）。
読んでほしい相手がまだ招待されていなければ、**サイトの管理画面で相手の Google アカウントを招待する**と一言添える。
ログインなしで誰にでも見せたいときは、**ページを開いて右下の「共有範囲」から公開に切り替えられる**
（URL はそのままで、公開用の URL が 1 本増える）。投稿し直しは要らない。

## ページの削除

ユーザーが「このページを消して」と依頼した場合。

```bash
node <リポジトリ>/bin/pages-publish.mjs --slug diagrams/api-basics --delete
```

確認を聞かれるので、**ユーザーに見せてから答える**。対話できない環境でだけ `--yes` を付けてよい。

消すのが公開ページ（URL が `/public/` で始まる）なら `--public` も一緒に付ける。付け忘れると、
同じ名前の「招待した人だけ」のページを探しに行って「そんなページはありません」で止まる。

どのスラッグか分からなければ、消したい URL をユーザーに聞く。**当てずっぽうで消さない。**

消すと URL は開けなくなるが、それまでに投稿した文章は版として残る。
「無かったことにする」操作ではない、とユーザーに一言添える。

## 守ること（禁止事項）

絵文字と日本語表記の扱いは、呼び出し側のスキルごとに違う。各スキルの手引きに従う。

- **React・shadcn/ui を使わない** — 静的なページに JS フレームワークは不要
- **動きで見せる表現・入力欄を入れない** — フェードイン、スクロール連動、自動で切り替わるカルーセル、フォームは禁止。読み手が触らないと中身が分からないページにしない
- **開閉トグル（`<details>`）は使ってよい。ただし `open` を付けて開いた状態から始める** — 補足・根拠・長い一覧を畳めるようにして本筋を短く見せる用途に有効。畳んだ状態を既定にしてはいけない理由は 2 つある: ①その中身は読み飛ばされる前提になる ②**PDF 出力で中身が丸ごと落ちる**。テンプレートの print CSS に印刷時に開く指定を入れてあるが、ブラウザによっては効かない（新しい Chrome は別の仕組みで畳むため）。確実な対策は `open` を付けること。**本筋の主張・結論・数字はトグルの外に置く**
- **`<style>` タグを追加しない** — スタイリングは Tailwind CSS クラスで行う。インラインの `style` 属性も避ける。
 **例外は図の「貼る一式」に入っている `<style>` 1 枚だけ**で、これは自分で書くものではなく写すもの
- **`<script>` を追加しない** — テンプレートに含まれるもの以外の JavaScript は禁止。
 **例外は図の「貼る一式」ただ 1 つ**で、`<リポジトリ>/src/templates/mermaid.html` を
 丸ごと写す形でだけ足してよい（自分で書かない・写したものを直さない）。
 配布版のサイトは、保存のときにページの仕掛けを検査し、配信のときにも実行を制限している。
 自分で書いた script は、そこで断られるか動かない
- **コメント機能の script タグを書かない** — 配信時にサーバー側が自動で差し込む。ページ側で読み込むと二重になる
- **外部リソースを追加しない** — テンプレートに含まれる CDN 以外の外部読み込み（画像 URL・フォント・追加 CDN）は禁止。ページに載せる画像は同じフォルダに置いて相対パスで参照する。
 図の道具の行き先は上の例外に含まれる。**配信のときに自分のサイトの置き場へ付け替わる**ので外から取ることにはならないが、
 付け替わるのは写したままの形だけ。短くしたり版を書き足したりしない
- **テンプレートの額縁構造を変更しない** — `<head>`・CDN 読み込み・meta タグはそのまま維持する（足してよいのは上の一式だけ）
- **画像を HTML に埋め込まない** — data URI にすると本文が重くなる（配布版は 1 回 4MB で頭打ち）。フォルダに置いて `--dir` で投稿する
- **人に見せたくない個人情報・お金の話・パスワードの類を載せない** — 投稿するたびに版が積まれ、後から書き換えも削除もできない。ページを消しても過去の版の文章は残り続ける。「後から無かったことにしたい」ものはそもそも投稿しない
- **グラデーション文字を使わない** — `bg-clip-text text-transparent` は PDF 出力時に透明になるうえ、
 生の色名を並べることになる（`from-blue-500 via-red-500` など）。額縁の逃げ道も外したので、
 見出しの 1 語を目立たせたいなら `text-ads-accent` にする
