# 体感速度（ホーム・切り替え・資料を開く・戻る）

人が毎日する場面を、本番と同じ条件で本物のブラウザで測り、目標（爆速）と CI の歯止めで守る。
測る道具は `tests/checks/browser/app-speed.mjs`、合格ラインは同じ場所の `app-speed-budget.mjs`、
仕掛けが外れていないかの検査表は `tests/checks/check-app-speed.mjs`。

## 何が遅かったか（2026-10-08 の本番の実測）

ログイン済みのブラウザで本番（pages.example.com）を開いて測った。読むだけ。

| 場面 | 本番の実測 |
| --- | --- |
| ホームを新しいタブで開く | 2.6〜3.8 秒（サーバーが文書を流し終えるまで。見た目の部品の取り寄せはそのあと） |
| 会社の資料・自分の資料・自分の活動・録音を開く | 2.3〜3.7 秒 |
| 画面の中の切り替え（ホーム → 会社の資料） | ホーム 2.7 秒・会社の資料 3.8 秒 |
| お気に入り・個人設定 | 0.3 秒 |
| 資料を開く | 本文まで約 0.3 秒・道具箱の問い合わせ 1 本ごとに 0.15〜0.3 秒 |
| サーバーの関数そのものの往復（保存先を引かない口） | 15〜25ms |

一覧の画面の検査は手元で 0.1 秒未満だった。**保存先が同じ機械にあると、
問い合わせを何回順番に待っても速く見える**ため、本番だけが遅いことに気づけなかった。

### 原因（大きい順）

1. **議事録の見てよいかの判定が、GitHub を 1 つずつ順に待っていた。** 一覧を描くたびに、録音から作った議事録のうち
   GitHub のリポジトリを使ったもの（本番 9 枚・リポジトリ 2 つ）について、リポジトリ 1 つにつき 2 回ずつ GitHub に聞いていた。
   答えを覚える仕組みが無く、録音を見てよい人かどうかを確かめる**前に**全員ぶん聞いていた（答えが変わらない大半の社員も待たされた）。
2. **保存先への問い合わせを、1 回の画面で 16 段に分けて順番に待っていた。** 本番の保存先は HTTP の受け口（Supabase の REST）経由で、
   1 回の問い合わせに 60〜75ms かかる（手元から検証用の受け口を続けて 12 回読んだ中央値 75ms。ネットワークの往復は 10ms）。
   サイドバーと画面が同じ問い合わせを別々に引き、名簿は「所属のまとまり → 生きているか → 許可」、議事録は
   「成果物 → つながり → 録音」と、それぞれ順に待っていた。
3. **戻ると読み直しになっていた。** 画面を開くたびに言語の控え（cookie）を同じ値で書き直していて、
   ブラウザが「開いてから cookie が変わった画面」と見なし、戻る・進むで画面をそのまま戻せなかった。
4. **押す前に何も取り寄せていなかった。** ワークスペースの画面は待ちの表示（`loading.tsx`）を持たないので、
   Next の既定の先読みは何も取らない。資料（`/internal/`）は別の文書なので、Next の先読みの外。
5. **資料を開くたびに、道具箱の部品 3.9MB（圧縮後 980KB）を全部読んでいた。** 8 割はスライドの直接編集の部品
   （見本集・見本の縮小図・旧版の操作部品）で、記事を読むだけの人には要らない。スマホでは道具箱が出るまで 1.8 秒かかった。

## 測り方

```bash
node tests/checks/browser/app-speed.mjs                       # CI の歯止めと比べる（本番の今の条件）
node tests/checks/browser/app-speed.mjs --target              # 目標（爆速）と比べる
node tests/checks/browser/app-speed.mjs --phone --target      # スマホの条件で、スマホの目標と比べる
node tests/checks/browser/app-speed.mjs --measure             # 測るだけ
node tests/checks/browser/app-speed.mjs --trace /,/library    # 1 回の要求で保存先へ送った文を、時刻の順に出す
node tests/checks/browser/app-speed.mjs --app <フォルダ>       # 組み立てを使い回す（無ければそこへ組み立てる）
node tests/checks/browser/app-speed.mjs --db-rtt 70 --db-workers 0 --measure   # 配布版の本番の条件（下）で測るだけ
```

**配布版の本番の条件**: 関数は東京（`vercel.json` の `hnd1`）、Neon はシンガポールで、保存先まで 1 往復約 70ms（`--db-rtt 70`）。
保存先へは直接つなぐので、HTTP の受け口の混み合いは無い（`--db-workers 0`）。比例の線の控えとは条件が違うので、絶対の線だけと比べるか
（`--measure` を外す）、測るだけにする。ブラウザとアプリの間の往復（配布版の実測で約 8ms）はこの台本では足していない。

| 本人の資料を新しいタブで開く | 278ms |

- 個人版として起こす（`PAGES_EDITION=personal`・設置した本人 `PAGES_OWNER_EMAIL`・`tests/support/serve-app.mjs` と同じ起こし方）。
  使い捨ての PostgreSQL・本番と同じ組み立て・本物の Chromium（人の Chrome と同じ新しい形のヘッドレスで、戻る・進むの控えを切らない）。
  本番の鍵には触れない。
- データは生きている資料 500・見る人を絞った資料 72（割合は会社版の本番の 827 のうち 119 に合わせた）。1 人のサイトとしては多めにして、
  資料の数に比例して遅くなる変更が数字に出るようにした（2026-10-14）。資料は本人が作り、絞った資料の名簿とコメントは招いた人。
  本文を持つ資料は検査の材料（`tests/checks/fixtures` の架空の資料）の写し。
- **保存先の重さ**: 保存先の前に中継を置き、行き帰りを半分ずつ遅らせる（`--db-rtt`、既定 30ms）。手元の直接の接続は 1 回の問い合わせで
  2 往復する（文の形を確かめる往復と実行する往復。`--trace` で 1 段がほぼ 2 往復ぶん進むのが見える）ので、30ms で 1 回約 60ms ＝ 本番の
  HTTP の受け口と同じになる。同時に開く接続は 12 本まで広げる（`DATABASE_POOL_MAX`。本番の HTTP 方式は同時に何本でも投げられる）。
- **保存先の混み合い**: 送った文を「働き手 2 人が 1 本 30ms ずつ順に片付ける」列に並べてから渡す（`--db-workers 2 --db-cost 30`）。
  本番の保存先は同時に投げると 1 本ずつが伸びる（下の「本番で分かったこと」）ので、並べないと「同時に投げれば速い」と誤って出る。
  この条件で直す前のホームは 0.80 秒と出て、本番の実測（サーバーが答え終わるまで 0.86 秒）と合う。`--db-workers 0` で並べない（前の測り方）。
- **配信の条件**: アプリの前に、本番の配信網と同じく文字の応答を圧縮する中継を置く（`next start` は圧縮しない）。検査用の組み立て
  （webpack）は、見た目の指定を作る道具（`tailwindcss-v3`）を本番の組み立てと同じく束に入れない（`tests/support/test-app-build.mjs`。
  束ねると「本文を描く前の待ちを外す」差し込みが毎回失敗し、本番より遅い条件で測っていた）。
- 押す前にリンクへ 0.3 秒とどまる（`--dwell`）。人はカーソルを運んで止め、少しとどまってから押す。
  とどまる長さの公表された中央値は見つからず、手引きの類は 0.3〜0.4 秒を挙げる（[instant.page](https://instant.page/)・
  ある病院のサイトの観察で 322ms と 545ms（[harvv](https://harvv.com/research/contact-form-hesitation)））。短めの 0.3 秒にした。
  `--dwell 0` で、とどまらずに押した場合（キーボードの Enter など）も測れる。
- **戻る**は、資料の読み込みが落ち着いてから 1 秒置いて押す（`--read`）。人は資料を読んでから戻る。落ち着く前に押すと、資料の画面が
  まだ投げている問い合わせ（コメント・見た記録）と保存先の列で取り合い、戻る先の分が後ろに並ぶ（2026-10-08: すぐ押すと 0.41 秒、読んでから押すと 0.26 秒）。
- 1 回目は数えない（関数の立ち上がり）。各場面 5 回の中央値。CI の歯止めを超えたら 1 回だけ測り直す（上限の数字は変えない）。
- 結果は `PAGES_SPEED_EVIDENCE_DIR` の `speed.json`（1 回ずつの値・中央値・目標と歯止めの外れ）。

### 測れないもの

- **資料の裏開き（prerender）は、自動操作のブラウザでは測れない。** Chrome は自動操作の道具（DevTools）がつながっていると
  prerender を止める（`PrerenderingDisabledByDevTools`）。手元の計測では、代わりに働く HTML の先取り（prefetch）が使われた数字になる。
  人の Chrome では、触れて 0.2 秒とどまった資料はさらに裏で描き終えている。

## 本番で分かったこと（2026-10-08 の公開後）

公開の前後で、本番の画面をサーバーが答え終わるまでの時間を同じ方法で測った（ログインした管理者・ブラウザの中から 5 回・中央値）。

手元の計測（0.2〜0.3 秒）より 3 倍ほど遅かった。保存先の受け口の記録（Supabase の `edge_logs` の `origin_time`）を見ると、
**同時に 10 本以上を投げると、1 本ずつが単独のとき（27〜40ms）の 5〜10 倍（170〜300ms）に伸びていた**。行が数行しかない表でも同じなので、
問い合わせの重さではなく、受け口が同時に片付けられる数で決まっている。手元の PostgreSQL は同時に投げても伸びないので、
「同時に投げれば待ちは 1 本ぶん」という手元の見立てが本番では成り立たなかった。

そこで **1 回の画面で投げる本数を減らした**（`src/lib/identity/member-reads.ts`・`db/migrations/20261008112101_workspace_member_reads.sql`）。

- 本人まわりの小さな問い合わせ 13 本（管理者か・個人設定・星・記録を残さない・名簿・議事録の材料・共有された録音・GitHub のつながり・
  登録の名前・読めるの覚え・覚えを捨てた回数・最後の知らせ・ページの一覧の終わりの目印）を、保存先の関数 `workspace_member_reads` の 1 本にした。
  **関数は判定しない**（今までと同じ条件の行を返すだけ）。GitHub の鍵の欄は返さない。使うのは画面を描く 1 回の中だけで、窓口では今までどおり 1 本ずつ読む。
  読めなかった欄は、使う側が今までの読み方に戻る。
- ホームの未解決のコメントと、今の版の形式は、目印を 40 件ずつ URL に並べていたので、資料の多い人（管理者は全部の資料が自分のもの）は
  10 本・3 段に分かれていた。一覧を本文で渡す関数（`open_page_comments`・`current_page_kinds`）の 1 本にした。
- 1 回の表示で保存先へ送る文: ホーム 20 → 8 本、会社の資料 15 → 6 本（`--trace`）。最初に同時に投げる本数は 12 → 3 本。

### 道具箱の最初の読み込みを軽くする（2026-10-08・4 回目）

道具箱の最初の読み込みに、入力の確かめの部品（zod・380KB）が入っていた。入ってくる道は 3 つで、どれも記事を読むだけなら要らない。

- 図の元の文を控える口（`keepMermaidSource`）が本文の書き出しの部品の中にあり、書き出しの部品がスライドの設定を経て zod を連れてきた。
  控える口だけを `src/lib/html/mermaid-source.ts` に分け（名前も控え方もここが正本）、書き出しの部品は使うとき（入口を置いて手が空いたら先に）読む。
- コメントの印を置くための本文の索引が、スライドの公開の補足を並べる部品を常に読んでいた。スライドのページでだけ読む。

## 保存先とのつなぎ方（2026-10-14・配布版）

配布版の設置は、関数が東京（`vercel.json` の `hnd1`）、Neon がシンガポール（Neon に東京は無い）で、1 往復が約 70ms 離れている。
「押してから切り替わるまでが遅い」の申し出を受けて、問い合わせの数から測った。

- **N+1 ではなかった**。記事を開くと保存先への文は 1 本（1 段）、ホームと一覧は 5 本（2 段・同時に投げる）。資料の数で増えない。
- **遅さの大半はつなぎ直しだった**。使っていない接続を 20 秒で閉じていたので、読んでから次を押す人はほぼ毎回つなぎ直し
  （暗号の握手・型の読み込み）、1 回で約 0.35 秒かかっていた。
- **文 1 本が 2 往復していた**。postgres.js は `unsafe()` の文を既定で覚えない（全体の `prepare` を変えても効かない）ので、毎回
  「形の確認」と「実行」の 2 往復になる。

直したこと（`src/lib/db/database.ts`）:

- 使っていない接続を 240 秒保つ（`CONNECTION_IDLE_SECONDS`）。Neon の無料の保存先が眠るまで（5 分）より短くして、眠る仕組みを邪魔しない。
- 形の決まった文（`compileQuery` の `stable`）と保存先の関数の呼び出しは形を覚える。`in` の並びと複数行の保存は件数で形が変わるので覚えない
  （覚えた形は接続ごとに溜まる）。接続を束ねる中継（Neon の `-pooler`・Supabase の `pooler.supabase.com`・`pgbouncer=true`）の宛先では覚えない
  （中継によっては覚えた形が別の接続へ渡って壊れる。`canPrepareStatements`）。
- 2 つは組みでしか効かない。閉じると覚えた形も消えるので、形を覚えるだけでは速くならない（下の表）。
- 接続を長く保つと、関数の一時停止明けに、止まっている間に相手が閉じた接続を使うことがある。読むだけの文（select）は接続が無くなっていた
  ときだけ 1 回やり直す。書き込みと保存先の関数はやり直さない（届いたか分からない書き込みをやり直すと二重に書きうる）。

| 一覧から記事を押して本文が出るまで／一覧を開いて出るまで（読んで 25 秒後に押す・4 回の中央値） | 記事 | 一覧 |
| --- | --- | --- |
| 直す前（20 秒で閉じる・覚えない） | 574ms | 722ms |
| 形を覚えるだけ | 586ms | 712ms |
| 保つだけ | 204ms | 344ms |
| **保つ＋形を覚える（今の形）** | **137ms** | **196ms** |
| 関数をシンガポールへ移す（20 秒で閉じる・覚えない） | 235ms | 230ms |
| シンガポール＋保つ＋形を覚える | 209ms | 198ms |

測り方: 個人版の本番の組み立て・使い捨ての PostgreSQL（資料 41）・本物の Chromium。保存先の前の中継で 1 往復 70ms（新しい接続は握手ぶん 2 往復を足す）、
ブラウザとアプリの間に 1 往復 8ms（シンガポールの行は 75ms）を入れ、押す前にとどまらない（先読みが効かない厳しい側）。
当時の `tests/checks/browser/app-speed.mjs` は会社版の部品を読んでいて配布版では組み立てが通らず、同じ考え方の使い捨ての台本で測った
（その後、個人版で起こすように直した。配布版の条件は上の「測り方」）。

関数をシンガポールへ移す案は採らなかった。東京のままでも同じ速さになり、移すと設置済みの人に設定のやり直しが要り、画面からの窓口の呼び出しが
1 回ごとに国をまたぐ。Neon の無料の保存先が眠ったあと（5 分空けた最初の 1 回）と関数の起動の遅さは、ここでは測れていない。

## 合格ライン

`app-speed-budget.mjs` に 3 つある。CI を赤にするのは下の 2 つ（歯止め）で、目標は届いたかを表に出すだけ。

| 線 | 何のため | 値 |
| --- | --- | --- |
| 目標（`TARGET`・スマホは `PHONE_TARGET`） | 人が「待った」と感じない線。毎回、届いたかを表に出す | 新しいタブ 1 秒（2 回目 0.7 秒）・切り替え 0.3 秒・資料の本文 0.5 秒・道具箱 1 秒・戻る 0.3 秒・スライド 1 秒・画像 30 枚の資料 1 秒。スマホは新しいタブ 2 秒・資料 1 秒・戻る 1.5 秒 |
| 絶対の線（`GUARD`） | 「はっきり遅くなった」を捕まえる。CI の台のばらつきでは赤にしない | 目標のおよそ 1.5〜2.5 倍（新しいタブ 1.5 秒・2 回目 1.2 秒・切り替え 0.6 秒・本文 0.8 秒・道具箱 1.8 秒・戻る 0.75 秒・スライド 1.5 秒・その道具箱 2.2 秒・画像 30 枚の資料 1.2 秒）。直す前の 2.6〜3.1 秒と、画像を 1 枚ずつ確かめていた頃の 1.83〜1.85 秒は必ず掛かる |
| 比例の線（`RATIO` と `app-speed-baseline.json`） | 絶対の線より手前で、じわじわ遅くなるのを捕まえる | CI の台で測った控えの **1.5 倍を超え、しかも 150ms 以上遅い**とき外れ。小さい数（切り替え 50ms など）は 1.5 倍でも体感が変わらないので、差の下限で揺れを拾わない |

- 1 秒は「待った」と感じ始める境目、0.3 秒は押した手応えのまま中身が出る長さとして置いた。
- 目標そのものを歯止めにしていたころは、CI の台で資料の道具箱が中央値 0.88 秒（最遅 1.09 秒）・戻るが 0.32 秒と線のすぐそばで揺れ、
  遅くなっていないのに赤になりうるので、絶対の線は緩め、細かい後戻りは比例の線に任せた（2026-10-08）。
- **絶対の線は緩める方向に動かさない**（検査表が「直す前の遅さを捕まえる」「目標の 2.5 倍より緩めない」を見る）。
- **いまの控えは会社版の CI の台で測った数**（会社のデータ・HTTP の受け口の保存先）。この配布版の CI には体感速度の計測が無いので、
  個人版では取り直していない（2026-10-14 に決めた。手元の Mac で取り直すと下の決まりに反する）。取り直すには CI に計測を足してから下の手順で。
- 比例の線と比べるのは CI と同じ既定の条件（パソコン・とどまる 0.3 秒・保存先 30ms）のときだけ。控えは **CI の台で測った数**から作る
  （手元の Mac は速いので、手元の数で作ると CI が毎回赤になる）。取り直すのは、速くした PR が main に入ったあとと、
  わざと遅くしてよいと決めたときだけで、理由を PR に書く。**CI の結果を 2 回分以上渡し、項目ごとに大きいほうを控えにする**
  （CI の台は同じコードでも資料の道具箱が 0.51〜0.88 秒と揺れる。たまたま速かった 1 回を控えにすると、何も遅くしていない PR が掛かる）:

```bash
gh run download <実行の番号> -n app-speed-results -D /tmp/app-speed-1
gh run download <別の実行の番号> -n app-speed-results -D /tmp/app-speed-2
node tests/support/app-speed-baseline.mjs /tmp/app-speed-1/speed.json /tmp/app-speed-2/speed.json
```

## 先読み

決まりの正本は `src/lib/pages/prefetch-policy.ts`。

- **画面（ホーム・自分の資料・お気に入り・自分の活動・会社の資料・個人設定）**: リンクの上にマウスを止めた・
  キーで選んだまま 0.1 秒たったら、Next に中身まで取り寄せさせる（`router.prefetch` の `FULL`）。見える範囲に入っただけ・
  通り過ぎただけでは取らない（一覧の 50 行ぶんをサーバーに描かせない）。取り寄せた中身を使うのは 30 秒まで（`next.config.ts` の `staleTimes.static`）。
- **押す直前には始めない。** Next は、届く前の先読みを待たずに同じ画面をもう一度取りに行く（`navigation.js` の `navigateImpl` は、
  取り寄せが終わった控えしか使わない）。触れた瞬間に始めていたころは、すぐ押すとサーバーが同じ画面を 2 度描き、手元の計測では切り替えが
  2.42 秒に悪化した。だから「とどまったら始める・押し始めたら始めていない分はやめる・指で触れたとき（触れてから押すまでが短い）はしない」にしてある。
- **資料（`/internal/`・`/public/`）**: 行の題と、サイドバーのお気に入りのリンクに触れて 0.1 秒とどまったら、その 1 枚だけを裏で開く宣言
  （Speculation Rules の URL の一覧の形）を差し込み、ブラウザが裏で描いておく。押した瞬間に差し替わる。別の資料に触れたら宣言を
  差し替える（外した宣言の裏開きはブラウザがやめる。裏で開くのはいつも 1 枚）。受け皿として、触れて 0.2 秒とどまったとき・押し始めたときに
  開く宣言（`moderate`）も置いてある（指で触れたとき・差し込みが動く前に押したとき）。対応しないブラウザでは何も起きない。
  ブラウザ任せの 0.2 秒だけだったころは、本番の資料は本文が届くまで 0.15〜0.2 秒・スライドは 1 秒かかり、マウスを止めてすぐ押すと
  裏で描き終える前に押すことになっていた（2026-10-08 の本番の実測）。始めるのを 0.1 秒早めて、押したときに描き終えている回を増やす。
- **裏で開いた資料は、表に出るまで「見た」と控えない**（`src/widget/comments/comments.ts` の `rememberView` が `prerenderingchange` を待つ）。

## 道具箱の部品を分ける

資料のページに差し込む道具箱の部品は、入口 1 本と、あとから読む部品に分けて組み立てる（`scripts/build/widget.mjs`。esbuild の分割）。

- ページへは `<script type="module">` で差し込む（`src/lib/pages/content.ts`）。`defer` と同じく本文を読み終えた直後・DOMContentLoaded の前に動くので、
  図の原文を描かれる前に控える順番は変わらない。
- **記事を読むだけの人に送るのは、入口と最初に必ず読む部品だけ**（3.9MB・圧縮後 980KB → 1.3MB・圧縮後 359KB）。
  直す画面（記事・スライド・動画）の部品は `src/widget/editor/loader.ts` から、発表者画面の部品は発表を始めたときに読む。
  **直せる人の画面だけ、道具箱が落ち着いたあとの空き時間に直す画面の部品を先に読んでおく**（押した瞬間に開ける）。
- 分けた部品は入口と同じ階層（`/comments-widget.js/comments-widget-chunk-<中身の印>.js`）で配り、名前に中身の印が入るので 1 年持たせる。
  前の版の部品（公開をまたいで開いたままの画面が読みに来たもの）は中身の違うものを返さずに断り、直す画面の入口が 1 行で読み込み直しを頼む。
  印の無い行き先・古い印の行き先は、今の入口を読みに行かせる小さな読み込み役を返す。
- **入口が最初に必ず読む部品は、入口と同時に頼ませる**（`<link rel="modulepreload">`。名前は組み立てが静的な import をたどって
  `src/widget/dist/stamp.json` の `preload` に書き、`src/lib/pages/content.ts` が入口のすぐ前に置く）。入口を読み終えてから部品を頼む 1 往復が消え、

  （本文を描くための読み込みより先に回線を取らない・`docs/design/page-loading.md`）。優先度を低くしても本文は速くならず、
  スライドでは画像の後ろへ回されるだけだったので、既定のままにしてある。

  `src/widget/deck/edit/state.ts` に切り出してある。

## 戻る（そのまま戻せる条件）

Chrome は「保存禁止（`Cache-Control: no-store`）の画面」でも、次の 2 つを満たせば戻る・進むでそのまま戻す
（[Chrome の説明](https://developer.chrome.com/docs/web-platform/bfcache-ccns)）。

1. 開いてから cookie が変わっていない → 言語の控えを書き直さないように直した
2. その画面の中で、保存禁止の応答を `fetch` で受け取っていない → 画面の切り替えと先読みの応答（Next の RSC）は保存禁止で返るので、
   1 度でも切り替えた画面は読み直しになる（スマホのように切り替えずに資料を開いた画面は、そのまま戻る）

読み直しになっても、ホームを組み立て直すのは 0.25 秒なので目標に入る。応答を「毎回確かめる（`private, no-cache`）」に変えれば
いつでもそのまま戻せるが、見る人を絞った資料の題もブラウザの保存領域に残りうるので、変えていない（2026-10-08 見送り）。
