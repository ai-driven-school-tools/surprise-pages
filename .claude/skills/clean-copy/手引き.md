# 原本を清書して自分のサイトで配る

完成した Markdown・テキストを、文章・数字・順序を変えずに機械で HTML に変換して配る。
**LLM は本文を読み直して構成・表・図・色・改行を判断しない。HTML も作業用 Markdown も手書きしない。**
同じ原本・公開設定・変換器・共通の額縁なら、同じ HTML ができる。

既定は「招待した人だけ」（自分と、サイトに招待した人がログインして開ける）。公開対象と公開先がすでに指定されている依頼は、その範囲で実行する。
原本がなく新しく書き起こすなら explain-page、HTML スライドを新しく作るなら explain-deck を使う。
原本に含まれるスライド指示の清書は、このスキルが担当する。

## 呼び出すのは 1 本

この手引きの隣にある `scripts/run.py` を**実行する**。コードやデザインの参照資料を読み直す必要はない。
依存は Python 3 の標準ライブラリと、このリポジトリの投稿コマンド（`bin/pages-publish.mjs`）。追加の Python パッケージは不要。
額縁・投稿コマンド・投稿先・ログイン情報の置き場は自動でたどる（このリポジトリと、投稿コマンドの設定から）。
Windows で `python3` が見つからないときは `python` か `py` で同じものを呼ぶ。
`<リポジトリ>` はこの手引きの**実体**から 3 つ上のフォルダ（近道越しに見えていても近道の先で数える）、`<スキル置き場>` は `<リポジトリ>/.claude/skills`。
コマンドはいま開いているフォルダのまま打つ。

### 公開設定があるとき（複数の原本・複数ページ）

```bash
python3 <この手引きのフォルダ>/scripts/run.py publish-bundle <案件の公開設定.json>
```

**登録済みの公開設定をそのまま使う。** 毎回原稿を読み、結合順・公開先・表示形式を決め直さない。
原本と公開先を自動でたどり、全件の検査・変換・照合が通ってから、設定順に公開する。
保存された HTML と素材を取得して照合し、一致して初めて成功とする。すでに一致しているページは投稿を省く。
途中で止まったら、問題を解決して同じコマンドを再実行する。成功済みのページに余計な版を作らない。

- 公開せず検証だけ行うときは `--dry-run`。通信も行わず、生成物と照合結果を一時領域に残す。
- 一括公開の成功時は一時生成物を片付ける。検証のため残すときだけ `--keep`。
- 原本の文章・数値・順序、表の各マス、図やコードの空白が一致しなければ、**どのページも投稿しない**。
- ページ間リンクは公開設定に沿って変換する。登録していないローカル資料は、確定した GitHub の出所へつなぐ。
  出所や見出しが不明なリンクを推測で直さない。参照先を勝手に公開対象へ追加しない。
- 画像・音声・動画のローカル素材も一緒に送る。本文が同じでも素材が欠けていれば更新する。
- 一括公開は「招待した人だけ」。公開用の設定を推測して作らない。

### 原本が 1 ファイルのとき

```bash
python3 <この手引きのフォルダ>/scripts/run.py publish 原本.md \
  --slug reports/kickoff --description "一覧と OGP に出る 1 文"
```

原本の所在と公開先を確かめ、1 回実行する。検査・体裁の修復・変換・照合・投稿・片付けまで通る。
原稿の表・スライド指示を読みやすい囲みで出すときは `--layout manuscript` を付ける。
1 行 1 息で書かれた台本（読む行が 1 つずつ段落になっている原稿）は `--layout script` を付ける。
読む行は濃く詰め、`※` で始まる注記と、見出しに空行を挟まず続く段落（状態・尺の添え書き）は
小さく薄く出し（字下げはしない）、原本の改行をそのまま見せる。字は 1 文字も変えない。
通常の清書は表示形式を指定しない。公開（ログインなしで誰でも読める）はユーザーが明示したときだけ `--public --yes-public` を付ける。

オプションと区間ごとの切り分けは `run.py --help` と各コマンドの `--help` が正本。
変換規則は `run.py mapping`、検査コードは `run.py codes` で確認する。手引きに一覧を転記しない。

## 公開設定を初めて用意するとき

案件の原本の近くに、公開先と原本の順番を記した JSON を 1 つ保存する。
以後の実行ではこれを再利用する。案件固有の原本一覧やスラッグを汎用スキルへ埋め込まない。
**設定の書式と検証の正本は [scripts/cleancopy/bundle.py](scripts/cleancopy/bundle.py) の公開設定の読み込み処理。**
以下は形式の例で、実際のパス・表題・公開先は依頼に合わせる。

```json
{
  "version": 1,
  "pages": [
    {
      "id": "manuscript",
      "slug": "lectures/sample/manuscript",
      "title": "講義原稿",
      "layout": "manuscript",
      "sources": [
        { "id": "doc-01", "path": "原稿/01.md" },
        { "id": "doc-02", "path": "原稿/02.md", "collapsed": true }
      ]
    }
  ]
}
```

パスは**公開設定からの相対位置**。原本の順番・識別子・折り畳みの指定がそのまま表示になる。
既存ページの出し直しでは、同じ公開先と原本の識別子を使い、見出しへのリンクを保つ。
設定を作ったら `publish-bundle ... --dry-run` で全件を確認し、同じ設定で公開する。
新規対象の範囲が依頼から特定できない場合は、その範囲の指定が必要。すでに指定済みの範囲を聞き直さない。

## 忠実さの線引き

**入れ物は機械が整える。中身は変更しない。**

清書には、閲覧側が見出しから目次と現在地を自動生成できる印を付ける。
パソコンの固定目次とスマホの現在地表示は共通の閲覧機能が担当するため、
ページごとの目次・追従処理を手書きしない。原本の名前を明示した場合だけ、その名前も印として渡す。

- 誤字・表記ゆれ・数字の矛盾も原本のまま出す。気づいても、この処理中に本文を編集しない。
- 見出し・引用・表・箇条書き・コードは Markdown の構造どおりに扱う。囲みの中の表や図も潰さない。
- 原本の Mermaid は図として出す。原本にない図・要約・説明・注記は足さない。
- 新しい説明を作ってよいのは、依頼に沿ったページ表題と一覧用の説明、目次のラベルだけ。本文の一部にはしない。
- 照合は、表示される本文の順番、表の行列、コードの改行・字下げまで機械で比較する。
  文字数が近いだけで通さない。検査の詳細は [scripts/cleancopy/verify.py](scripts/cleancopy/verify.py) が正本。
- 囲みの閉じ忘れなど、機械が文章を変えずに修復できる体裁は自動で直す。原本には書き戻さず、結果へ記録する。

## 止まったとき

返る JSON の `error` と `next` に従う。**原本や生成 HTML を手で修正して検査を回避しない。**

ログインが必要なら、ユーザーに `node <リポジトリ>/bin/pages-publish.mjs login` を打ってもらい、済んだら同じ呼び出しを再実行する。
変換や照合で止まったら、問題の原本と理由を報告する。原本の編集は別の執筆作業として扱う。
原本ごとのファイル名・文字数を通常表示から畳む場合は、その `sources` の項目に `"collapse_source_note": true` を指定する。本文や出典情報は削除せず、「文書の情報」を開くと確認できる。既定は従来どおり表示する。議事録のように本文だけを読みやすく見せたいときに使う。

通信が失敗しても、保存されているかを推測して再投稿しない。一括公開は次の実行でも保存内容を最初に照合する。
複数ページの公開は順次行われるため、途中失敗で一部だけ更新される場合がある。全ページが成功するまで完了扱いにしない。

投稿まわりの切り分け（投稿先・ログイン）や削除だけは、`<スキル置き場>/_shared/references/投稿の手順.md` の「投稿の下ごしらえ（前提確認）」「ページの削除」を読む。
額縁を手書きしたり、別の公開経路に切り替えたりしない。

## 出所と完了報告

各原本の末尾に、機械が出所と文字数を付ける。確定した Git の原本だけコミットへのリンクを付け、
未コミットなら作業中と示す。単一原本の公開では手元のパスとリポジトリ名を出さない。

一括ページには原本ごとの専用の印を付ける。単一ファイル用の `data-source-*` は付けず、
最初の原稿だけの単一ページと取り違えられないようにする。
**一括ページの更新は、必ず案件の公開設定から実行する。**

完了報告は、返された URL と検証結果、体裁を修復した件数を短く伝える。
一括公開では、更新したページと変更がなく省略したページを区別する。内容の要約は作らない。
単一原本なら返された `report_draft` を土台にする。本文は変更していないことも伝える。

## コメントを見て中身を直すとき

清書の HTML は完成見本なので、**HTML を直して出し直さない。** 直すのはマークダウン原本。

1. 読むスキルの `revise` が `page-out/原本.md` と `コメント.txt` を置く
2. コメントが指している文を、`原本.md` で差し替える
3. このスキルの `publish` に、その `原本.md` を渡す。スラッグと `--public` は元のまま

見た目だけの指摘は、このスキルでは機械が決めた体裁なので、HTML を触らず報告に残す。
`revise` が原本を取れずに止まったら、ユーザーに原本のファイルを渡してもらう。HTML から文章を復元しない。
