# スライドのデザインと着せ替え

「何を持ち帰ってほしいか」を先に決め、内容に合う構図を選ぶ。スライド全体の一文の結論を定めてから、必要な根拠を配置する。見た目は後から着せ替えられるので、文章量とレイアウトを配色に依存させない。

## 共通部品と見本

- 見た目の正本: `src/deck-design/styles.css`、設定・プリセットの正本: `src/lib/deck/design/design.ts`。
- 描画は `src/deck-design/runtime.ts`。`pnpm build:deck-design` で **`src/templates/deck-design.html`** と配布用検査を組み立てる。生成物は直接直さない。
- 新しい資料には `src/templates/deck-design.html` と既存の `src/templates/deck.html` の両方を、設定JSONの後、`head` の中に貼る。埋め込んだ時点の見た目を持ち歩く。配信時に最新版を差し込まない。
- 手本: `tests/checks/fixtures/internal/example/deck-design-presentation.html`（プレゼン）、`deck-design-proposal.html`（提案）、`deck-design-report.html`（報告）。検査用の架空資料であり、公開済みページの正本ではない。
- 旧 `deck-showcase.html` は以前の資料の互換検査用。新規作成では新しい3つを使う。

## 最初の表示

共通部品は本文より前に置く。紙の幅・16:9の高さ・余白は書体や図の準備を待たずに確定する。
読み込み表示は実物の寸法を消さずに重ね、指定された枚への着地後に解除する。
書体は初回だけ2秒で代替表示へ切り替え、後から届いた書体で読み位置を動かさない。
閲覧の準備と編集開始の準備は別に扱い、編集は全体の描画完了を待つ。
既存資料は保存済みの共通部分を更新する必要がある。配信時に独自処理を置き換えない。

## 情報量で構図を選ぶ

| 用途 | 主役 | 組み方 |
| --- | --- | --- |
| プレゼン | 一文、数字、写真 | 大きな文字と余白。64〜96pxの主役、24〜32pxの補足 |
| 説明・提案 | 判断と根拠 | 24〜28pxの本文。比較・左右対比・手順・関係図 |
| 読む資料 | 結論と検証可能な情報 | 20〜24pxの本文。表・グラフ・要約・出典を階層化 |

1枚に主張は1つ。根拠が複数あってよい。目次・章扉・結びを機械的に増やさない。「表紙は字だけ」「3項目まで」とは決めない。写真の意味や比較の関係に合わせて構図を組む。

使える部品は表紙、一文、写真＋説明、比較表、大きな数、棒グラフ、手順、日程表、関係図、要約、結び。手本の組み合わせを変えてよい。無意味なカードの列にはしない。新しい構図も共通の目盛り・色の名前・読み順に従えばよい。

### 主張の競合を許さない

**一枚を見て「何が言いたいか」を一文で答えられない構図は不合格。** 見出しが一つでも、本文に別の大きなコピーや抽象的な言い換えを置けば、主張は二つに見える。先に持ち帰る一文を決め、本文の各要素を「根拠・具体例・手順・出典・条件」のどれかに位置づける。役割を説明できないコピーは削るか、主張そのものと入れ替える。

- 製品紹介は「何ができるか」を主張にし、画面はその具体例、本文は画面の見方にする。見出しの下へ別の広告コピーを置かない。左右構成では、主張そのものを左の文字群へ置く。上段にもう一つの見出しを足さない。
- 質問は問いを一か所に置き、本文は判断材料にする。一般的な質問の下へ、もう一つの大きな質問を置かない。
- 引用は主張を支える証言として配置する。別の大きな結論を作らない。
- 根拠が複数ある場合は、主張を決める数字と背景の数字の強さを分ける。すべてを同じ大きさにして読者に結論を選ばせない。
- 先頭の主張以外の文章を強く見せる場合も、同じ主張の根拠・具体例であることが必要。本文の見出し・証言は通常24〜32px。大きな数字や数式は主張そのものを裏づけるときに使う。

出す前に、本文を一度隠して主張だけで意味が通るか、次に本文を戻して別の主張と競合しないかを実画面で確認する。文字サイズ・はみ出し・操作の検査が通ることは、この判断の代わりにならない。

### 書体と見出しのあしらい

完成スタイルには配色だけでなく、日本語と英数字の書体の組み合わせ、短い罫線・角のあしらいも含む。書体の組は `src/lib/deck/design/typography.ts` が正本。端正なゴシックは Noto Sans JP と Inter、柔らかなゴシックは Zen Kaku Gothic New と Manrope。見出しに明朝を使う組は Noto Serif JP と Manrope、本文は Noto Sans JP と Inter にする。本文と見出しを同時に明朝へ変えない。

利用者は完成スタイルを一つ選ぶだけでよい。書体やあしらいだけ変えるときは「細かく調整」に置く。書体を意図して変える場合は改行も変わりうるので、全枚の枠内への収まりを確認する。色だけの変更や入力の開始・変換中・終了では書体や寸法を変えない。

フォントは公開ライセンスの固定した原本を `vendor/deck-fonts/manifest.json` に記録し、配信の専用口から配る。個人の端末のフォントに依存させない。選んだ書体の全文字を読み込んでから適用し、新しい漢字を入力した瞬間に追加の部分フォントを取得しない。読み込みに失敗したら設定を確定せず、再試行できるよう知らせる。旧形式の資料に新しい書体設定だけを保存して表示を壊さない。書体を含む設定は第3版の共通部品を埋め込んだ資料でのみ扱う。

### 文字と余白

- 1280×720。外側64px、12列・列間24px。余白8px刻み、細部4px刻み。
- 文字の目盛りは20 / 24 / 28 / 32 / 40 / 48 / 64 / 80 / 96px。本文は20px未満にしない。SVGの文字も同じ。
- 日本語の見出しは意味のまとまりで折り返す。単語や句読点だけの最終行を避ける。通常文を勝手に改行しすぎない。
- 全体を縮めたりフォントを自動縮小して収めない。内容整理→構図変更→枚の分割の順で解決する。
- 1pxの線は表の行・図の関係・引用の境目など、読む意味があるときだけ。見た目の中心の微調整は1px単位でよいが、理由をその箇所に記す。
- `dd-body` は本文の残りの領域を使い、`dd-footer` は下の同じ位置に出す。画像・動画を横幅から大きくするときも、本文の残り高を上限にして見出しや脚注へ重ねない。背景の疑似要素は共通部品が予約している。本文に装飾要素や文字を足さない。
- スマートフォンでは構図のまま縮小する。情報量のある表を小画面の一覧でも大きく読めるとは保証しない。発表・拡大・印刷を含めて確認する。

### 結論と根拠を組む共通の型

標準の本文は `.dd-composed` とし、`.dd-slide-heading` に小さな章名と48pxの結論、40px空けた `.dd-body` に根拠を置く。表紙と章扉は `.dd-composed-hero` で80pxの題名を中心に一まとまりにする。本文を画面いっぱいの大きな言葉に揃えない。

少ない情報は残りの領域の中央にまとめ、多い表・図・画像は本文領域を使う。表の本文は24px、行が多い表だけ `data-dd-density="compact"` で20pxにする。主要な数字は80px、図表内のラベルは20〜24px。図の名前と単位は結論より小さくし、軸と欄外で同じ単位を重ねて表示しない。

形式名や毎枚繰り返す資料の説明は、紙の外の公開補足へ置く。データの対象・期間・定義・個別の出典は本文に残す。見本では架空の例だという説明も公開補足に残す。内容・図の原文・数値・安定した目印を、見た目を直すために書き換えない。

見本集の入口は `.dd-catalog-cover`、用途から選ぶ一覧は `.dd-catalog-navigation`、構図の比較は `.dd-catalog-guide`。追加した順番にリンクを継ぎ足すのではなく、全形式を同じ案内の中で選べるようにする。紙そのものと、型の説明の役割を分ける。

### 一文と写真一枚の構図

同じメッセージと写真で構図を比較する実装は `src/lib/deck/card/message-image.ts` の10種類。配置の正本は `formats.css` の `.dd-message-image`。本文の6構図は一つの見出しと一枚の画像を持つ。表紙・章扉の4構図は、その見出しにセクション名・サブコピー・組織名・所属・氏名を任意で添えられる。構図名・用途・切り取り方は紙の外の公開補足へ置く。

表紙の文字は `.dd-message-image-copy` の一まとまりとして配置する。題名、補足、発表者情報の順に主従をつけ、項目ごとに座標を追加しない。任意項目が無ければ要素自体を出さず、空の箱や余白を残さない。発表者情報も普通の本文HTMLであり、着せ替え設定に複製しない。生成の共通処理は `scripts/generate/deck-catalog/message-image.mjs`。各段落に安定した目印を持たせ、既存の直接編集を使う。比較用の所属・氏名は架空の例。

**枠いっぱいの写真や大きな文字を使う構図は、基本的に表紙・章扉向け。** 本文の説明は、左右分割・上下配置など、情報を受け止める余白がある構図を優先する。全面写真2種、文字主役の余白、縦帯の4種は表紙・章扉として出力し、それ以外の6種は本文・結び向けとする。

切り取りは表示上だけで行い、元の画像を別ファイルに加工しない。全面写真に文字を重ねる場合は、文字の後ろの明暗を補正する。比較例では同じ一文・画像を保ち、写真や文を変えた差を構図の差と混同させない。生成は `scripts/generate/message-image-compositions.mjs`。

### 表紙・章扉・箇条書きの構図

追加18構図は `src/lib/deck/design/editorial-compositions.ts`（表紙5、章扉4、箇条書き9）。見た目は同じ `formats.css`、生成は `scripts/generate/editorial-compositions.mjs`。表紙・章扉は共通の題名グループと発表者グループを使い、項目を省略しても空の行を残さない。情報を左右に分ける場合も、文字量で列全体が伸縮しない構図にする。

箇条書きは `ul` / `ol` の一つの項目に画像・要点・理由をまとめる。3画像は三つの意味に対応する別々の素材を使い、画像のための飾り枠を足さない。画像の上下、横3列、縦3段、1項目を大きく見せる配置を目的で選ぶ。写真は被写体に合わせて切り取るが、説明用の絵は全体を表示する。絵の中へ説明文を焼き込まず、説明は通常の編集できる文字にする。

段階表示は全体→各項目。画像と説明を一組で強調し、文字の寸法や改行は動かさない。読む表示と印刷は常に全項目を表示する。`tests/checks/browser/deck-editorial-interaction.mjs` が実際の編集開始・入力・終了と段階表示の配置を確認する。

### 画像で伝える手順

`src/lib/deck/design/process-compositions.ts` の3構図は、横3列・縦3段・最初の一歩を大きく見せる手順。生成は `scripts/generate/process-compositions.mjs`。画像を添えた箇条書きとは区別し、`ol` に順番を持たせ、番号・矢印で読む方向を示す。画像・番号・見出し・説明は項目一つの焦点対象とし、子へ重ねて焦点を付けない。画像内に文字を焼き込まず、説明は直接編集できるHTMLにする。

文字だけの横手順も同じ考え方で、淡い面・48pxの番号・32pxの名前・20pxの補足を一組にする。余白は内側32px、番号と名前の間24px。最長の文字列から各段階の高さをそろえ、図の領域の中央へ配置する。条件付きの矢印は条件を省略しない。色の面は焦点と一緒に変化するが、形と文字の位置は変えない。

見本集では手順3構図を「流れ・関係の図」の先頭に置く。見本の配色は `scripts/generate/deck-catalog/appearance.mjs` にまとめ、表紙・章扉は奥行きのある光、本文は薄い傾斜、写真全面は写真そのものを使う。利用者の保存設定は引き続き優先する。すべての枚へ濃い背景や飾り枠を足すのではなく、情報の区切りと視線の進み方に合わせて面を使う。

### 配色とあしらい

会社テーマを指定されたら `bin/pages-publish theme surprise --out <新しいフォルダ>` で取り寄せる。
返る `theme.json` の `theme` を `data-deck-theme`、`design` を `data-deck-design`、`logo` を `data-deck-logo` の基本設定として
そのまま使い、同梱された `assets/` を原稿と一緒に投稿する。画面の新規作成と同じ設定・ロゴであり、
ロゴを描き直したりFigmaの資料作成に置き換えたりしない。`bin/pages-publish themes` で利用可能な一覧を確認できる。
この指定がある場合は、下の標準スタイル選択より優先する。会社テーマは社内版でのみ利用できる。

作成時は `src/templates/deck-styles.json` の完成スタイルから一つ選び、その `appearance` を基本設定の `document` に使う。配布用の設定は同じ正本から組み立て、手書きで複製しない。

設定画面では「完成スタイル」を選ぶだけで、下地と複数の色・濃さ・位置・広がりを一度に適用する。色を一つずつ選ぶことを前提にしない。調整は「細かく調整」の中にまとめ、閉じたままでも完成するようにする。比較資料は `scripts/generate/deck-gradient-study.mjs` で、同じ表紙と本文に12のスタイルを適用して作る。

プリセットは白・墨・藍・森・夕映え・オーロラ・パール・ライラック・氷青・薄明・霞・海辺。色と装飾の規則は**スライド内だけ**のもの。アプリの操作画面・文章ページ・清書の規則は変えない。

- 文字は `var(--dd-text)`、補足は `var(--dd-muted)`、線は `var(--dd-border)`。強調は `var(--dd-accent)` と `var(--dd-secondary)`。
- 色の値を構図のCSSへ焼き込まない。JSONの設定だけで指定する。図のラベル・グラフの値は色が変わっても残す。意味のある写真の色は着せ替え対象外。
- 背景の描き方は `src/lib/deck/design/background.ts` の一つの処理を、スライドと設定画面の見本で共用する。方向のあるグラデーションは薄い中間色を挟み、光は7段階で滑らかに薄くする。画像を背景として焼き込まず、保存した配色・位置・広がりから描く。
- 背景の淡い色と、意味を持つ強調文字・図の色を同じ濃さにしない。背景は指定色のまま混ぜ、強調は同じ色相から十分な濃さを計算する。利用者に読みやすい色の組み合わせを考えさせない。
- 色を重ねる層は一つの背景面にまとめ、その面全体に読みやすさを計算した濃さを適用する。層ごとに同じ濃さを付けて足し合わせない。動くのは背景面だけで、本文の寸法と位置は変えない。
- グラデーション・光・格子・波形は選択可能。位置・濃さ・大きさを変えられる。方向は直線グラデーションと格子で指定する。
- 新しい「斜めに重なる面」は、ロゴの上向きの角度を反映した2枚の背景。角度・位置・広がりを設定から描く。
  表紙では全面に広げて背景だけを動かす。本文は装飾のない均一な紙面とし、ロゴ・書体・余白で一貫させる。
  表紙はタイトル形式または表紙の構図で明示する。先頭という理由で本文を表紙扱いしない。
  表・グラフ・Mermaidのある枚にも装飾を置かない。動きを減らす設定と印刷では表紙の背景を静止する。
  この装飾には `data-deck-diagonal` を持つ新しい共通部品が必要。印だけを古い部品へ追加しない。
- 装飾は本文の後ろにだけ描く。本文の位置・行送り・寸法を変更しない。
- 自由な背景色でも文字のコントラストを維持するため、描画時に文字色と装飾の上限濃度を計算する。背景上の本文はこの文字色を使うこと。
- 動きは緩やかな背景だけ。標準は静止、オーロラは動き付き。動きを減らす端末設定と印刷では静止。画面外・非表示タブでは止まる。
- 配色は端末の明暗で変えない。表示・印刷とも保存した設定を使う。
- 素材は非公開の素材保管庫に置き、投稿の既存導線を使う。見本の外部写真参照を実際の資料に残さない。

## HTMLの設定

headの直下に基本設定を1つ置く。各枚に安定した `data-deck-id` を付ける（英小文字から始まる英数字とハイフン、80文字まで、資料内で重複不可）。`opening`、`revenue` のように内容で付け、並べ替えても変更しない。新しい内容の枚には新しい目印を付ける。

```html
<script type="application/json" data-deck-design>{"version":1,"document":{"background":"#ffffff","accent":"#2859dd","secondary":"#91b8ff","decoration":"none","intensity":40,"x":85,"y":20,"scale":100,"angle":135,"motion":false},"slides":{}}</script>
```

`slides` は必要な枚だけの初期設定。値の選択肢・数値の範囲は `src/lib/deck/design/design.ts` が正本。パレットの選択を含む、組み立て済みの設定は見本のheadから取れる。

- 色は6桁の16進数。濃さ・横位置・縦位置は0〜100、大きさ50〜150、方向0〜360、動きは真偽値。
- 基本設定と画面で保存した変更は別。利用者の設定はheadの `data-deck-appearance` に置く。作成者はこの領域を書かない。
- 適用順は基本の全体→基本の各枚→利用者の全体→利用者の各枚。「全体に合わせる」はその枚の個別指定を解除する。作成時にも個別設定のある枚では、全体に追従する目印も保存し、作成時の配色が復活しないようにする。
- UIから書き出すJSONは現在の適用先の有効な見た目だけ。読み込み先で全体／この1枚を選ぶ。本文・目印・会社のアカウント情報は含めない。
- 書き出した設定で新規作成するときは、JSONの `appearance` を基本設定の `document` に採用する。利用者の保存領域は新設しない。

## 関係と流れの図

図は「順番・状態・分岐・所属・受け渡し・期間」の問いに合わせて組む。少数の箱を画面いっぱいへ拡大せず、原寸の文字と余白から配置する。手順は番号・動詞・補足、状態は名前・定義・進む条件、分岐は質問と結果を別の列に置く。

- 原文は既存のMermaidのまま。共通部品が固定版の解析機能で読み、用途別に配置する。別の保存用JSONへ書き写さない。集合・四象限は従来の専用データを使う。
- 名前32px、補足・条件20px、日程の作業名28px。文字を縮めて収めない。長い名前は語句で折り、収まらない情報は枚を分ける。
- 名前と補足を分けるときは、図の文字列に改行を入れる。HTMLのpre内では改行タグを文字として残すため、次のようにエスケープする。

```html
<pre class="mermaid">flowchart LR
capture["記録する&lt;br/&gt;まず一文で残す"] edge-next@--&gt; organize["整理する&lt;br/&gt;背景を足す"]</pre>
```

- 箱から出入りする線は、24px以上まっすぐ伸ばしてから曲げる。複数の線は接続口を分ける。条件文を線の上へ重ねず、文字の外縁から24px離す。選択時にも字を太くして幅を変えない。
- 特別な形、リンク、独自の装飾など、対応できない原文は情報を落とさず従来の描画へ戻る。この場合も目視で確かめ、共通描画と同じ品質が保証されたとは扱わない。
- 日程は帯だけで長さを表し、文字・行間は固定。四象限の両端を示すときは、専用データのxEnds/yEndsへstart/endを指定する。横は左→右、縦は上→下に対応させる。

図の見本は既存の形式台帳にある14種類。見る人に関係のない実装説明を題名や脚注へ並べず、その図で判断することを題名にする。段階表示は全体を見せてから注目点を送る。節点・接続線を一緒に説明する段階では、両方を同じ段階の対象にする。

## 焦点を順に見せるとき

通常の読む表示と印刷は、常に全内容を同じ強さで読める形にする。焦点は発表で明示的に使う段階表示で、対象外も文脈を判別できる濃さを残す。全体を見てから細部へ進む枚は、最初の手順を `overview` にする。すぐ結論へ注目させる枚だけ、最初から対象を強調する。

読む表示の「順に見る」から各枚の段階表示へ入れる。発表中は段階名・件数と、前へ・次へ・全体の操作を使える。段階を変えても紙の大きさを変えない。公開の補足と動作の注釈は、読む表示・印刷・書き出しにも残す。

全枚の基準画像は焦点を解除した読む表示で撮る。焦点の確認画像は別にし、「全体 → 強調 → 次の強調 → 全体」の順で、現在の枚と手順の目印が一致していることを確かめる。薄くした要素の文字・線・項目名が判別できなければ不合格。

## 動画を使う

編集画面の「動画を追加」かファイルのドロップで、MP4・WebMを1本100MBまで追加できる。ブラウザで再生できる映像を選ぶ。追加前に端末内で1フレームだけを取り、最大1280×720の軽いプレビュー画像を作る。動画の圧縮・形式変換は行わない。

原稿から置く場合も、標準の `video` に `controls playsinline preload="none"` と `poster`、相対パスの `src` を書く。動画を自動再生しない。見出しで「何を見ればよいか」を伝え、映像は本文の領域に収める。印刷でも内容が分かるプレビュー画像を選ぶ。字幕の `.vtt` と文字起こしを添えられる。

再生前はプレビュー画像だけを表示する。画面外・別の枚・別のタブへ移ったときは停止して、通信と再生用のメモリを解放する。同時再生は1本まで。停止中は画面側だけ動画の参照を控え、再生操作で元の参照へ戻す。保存するHTMLや書き出す参照は変えない。再度再生すれば前の位置へ戻る。利用者が明示的に開いた小窓再生は継続する。編集画面では「動画を再生」で操作し、「編集に戻る」で配置を直す。

送信は2MBずつ、同時に2つまで。通信の一時的な失敗は同じ部分を再送し、進捗と中止を表示する。各要求は本文の編集権限を通り、非公開の一時保管からサーバーが順番に読み出し、8MBずつ1つずつ保管庫へ送って完成させる。動画全体をメモリに展開せず、ブラウザへ保管庫の鍵を渡さない。送信の印は利用者と資料に結びつき、2時間で失効する。中止・成功後に一時データを消し、取り残したものは24時間後から既存の日次処理で掃除する。完成した動画とプレビュー画像は履歴のために残す。

## 保存と原稿の取り込み

画面の編集権限を持つ人だけが保存できる。デザインは既存の編集画面と同じ保存・下書き・履歴を使い、同時に更新されたら保存せず知らせる。下書きは3日間、同じ版のときだけ戻す。

原稿を取り込むと、本文・配置は原稿へ更新し、**現在保存されている利用者の着せ替えはサーバーが引き継ぐ**。同じ目印の各枚の設定は残り、新しい枚は全体設定を使い、なくなった枚の設定は外す。取り込み側は原本を改変しない。利用者の設定を失う旧形式への変更は止める。

原稿との比較は保存済みの着せ替えだけを除く。通常の本文編集が消えるという警告はそのまま残す。デザイン変更だけで「本文が変わった」と誤って出さない。

## 画像を選ぶ順番を固定する

1. 検索の前に、必要な被写体・紙面上の幅と高さ・切り抜くか全体を見せるかを決める。画像を見つけてから無理に大きく使わない。
2. 決めた寸法を検索に渡す。候補の元寸法と切り抜きを計算し、表示の縦横2倍に足りない画像は候補から外す。同じ検索条件の元結果を再利用し、配置寸法や見せ方を変えたときは候補を計算し直す。
3. 候補の出典と構図を見て2〜3点に絞ってから取得する。見つからないときは検索語や構図を変え、小さい画像へ自動で戻さない。検索語を少しずつ変えて連打しない。
4. 取得した原画像を原寸で見て、ピンぼけ・圧縮の乱れ・引き伸ばし・透かしを除外する。検索結果の寸法だけで合格にしない。
5. 配置後に全枚を原寸で確認する。最後に正規の投稿コマンドが画質検査を自動で行う。未検査のまま投稿する別経路を作らない。

```sh
# 全面の表紙。切り抜いた後にも2560×1440相当の画素が必要
bin/pages-publish images search --query "探す対象" --width 1280 --height 720 --fit cover
# 右半分の写真を全体表示する場合
bin/pages-publish images search --query "探す対象" --width 560 --height 360 --fit contain
# 構図がまだ決まっていない表紙・全面写真だけの候補探し
bin/pages-publish images search --query "探す対象" --size large
```

寸法未定の大画像指定では長辺2560px・短辺1440px以上に絞る。寸法と見せ方が決まれば、配置条件を優先して探す。
候補数が0でも条件を緩めない。検索結果の寸法は取得前の情報なので、保存した実物と実際の切り抜きに対する検査は省略しない。

## 画像の画質を投稿前に止める

画像は1280×720の原寸で、実際に描く大きさの縦横2倍以上の画素を用意する。
`object-fit: cover` の切り抜きは、枠の寸法だけでなく、枠の外まで拡大される画像全体で計算する。
写真の背景も画像要素で置く。CSSの背景写真は未確認として止める。
小画面の縮尺や `srcset` が返す見かけの寸法を基準にしない。単なる拡大保存やAIによる補間で通さず、大きい原画像に替えるか構図を変える。

画像付きスライドは、正規の投稿コマンドが本文の送信前に同じ検査を必ず実行する。検査道具・ブラウザが無ければ投稿を止め、スキップする指定は用意しない。投稿コマンド3本だけの単体配布では画像付きスライドを出せないため、このリポジトリの依存関係か、検査を含むエージェント配布物を使う。

全枚を撮る前にも次を実行し、`ok: true` を確認する。足りない画像・読めない画像は停止理由になる。
既存資料はページ名を指定すると、その資料で閲覧できる保存済み素材だけを読む。認証を文書やブラウザへ渡さない。

```sh
node bin/deck-image-check.mjs path/to/index.html
node bin/deck-image-check.mjs path/to/index.html --page internal/decks/example
```

エージェントの変更案の描画検査も同じ基準で停止する。変更する枚に以前から粗い画像がある場合も、未解決として残す。
画素数は最低条件であり、ぼけ・JPEGの圧縮の乱れ・文字のにじみの合格証明ではない。全枚の原寸表示を目で確認し、粗い素材は数値が足りていても使わない。
写真の代わりに小さい画像を引き伸ばすことや、検査を飛ばして投稿することは禁止する。

## 出す前の確認

機械検査の「画像を取得できた」「枚の外へはみ出していない」だけでは合格にしない。枠内で画像が見出しを覆う、全枚のロゴが本文より強い、といった意味と見た目の欠陥は全枚の画像で判断する。

1. 3つの見本から必要な構図を選ぶ。直す前の全枚を順番どおり、1280×720の原寸と幅390pxの実際の表示で1枚ずつ撮る。幅390pxはChromium系とSafari/WebKit系の両方で撮る。撮る前に書体と画像の読込、グラフと図の描画完了を待ち、焦点を解除する。画像は投稿する素材の隣に置かず、検査専用の場所へ `001-<枚の目印>.png` のように同じ名前でそろえる。撮った枚の目印をファイル名と突き合わせ、予定した目印の集合と件数が一致すること、抜け・重複・直前の枚の写り込みがないことを確かめる。
2. 全枚を一覧でも見て、各枚について次を記録する。
   - **意味**: 3秒で一文の結論を拾え、その根拠が何か分かるか。
   - **視線**: 最初に見る主役から、見出し、根拠、出典へ無理なく進むか。
   - **主従**: 文字・数値・写真・図のどれが主役か明確で、ロゴや装飾が本文より強くないか。
   - **余白**: 原寸で左右端、見出しの基準線と行間、見出し下から本文上、本文下から脚注、画像の4辺、ロゴの端距離を1px単位で確かめる。見出し・本文・画像・脚注・ロゴが重ならず、画像が本文の枠内に収まり、見出しとの間が24px以上あるか。
   - **文字**: 見出しの不自然な折返しと行間、本文との距離、端の揃いを確かめる。図表の中は設定値だけでなく画面上の実寸を測り、図全体の縮小で20px未満になっていないかを見る。幅390pxでは第一視線と読める順を実際の大きさで目視する。Safari/WebKitで図の文字が横帯だけになったり、文字の箱が内容より小さく切れたりしていないかも全図で見る。
   - **流れ**: 同じ構図だけが続かず、数値・比較・図・写真が内容に合わせたリズムになっているか。
3. 複数の枚に同じ欠陥があれば先に共通部品を直す。内容固有の直しだけを各枚へ置く。隠す、文字を自動で縮める、枚ごとの座標で逃げる方法は使わない。
4. 直したあと、同じ大きさ・順番・ファイル名で全枚を再び撮る。直す前後を見比べ、重大な指摘が0件で、残す差が意図どおりだと説明できるまで繰り返す。交差0や数値範囲内でも、第一視線が定まらない、ラベルが読めない、余白が不自然、折返しが悪いものは不合格。検査値が合格でも同じ状態の画像が崩れて見える、または原寸と小画面の値が逆転するなど、数値と画像が矛盾したら必ず不合格に戻し、測る対象・縮尺・描画待ちのどこが違うかを解消する。1pxの補正は光学上の中心をそろえる実測差にだけ使い、理由を共通見本に残す。代表だけの確認で全枚の確認に代えない。
5. 配色とあしらいを変えても文字の位置・寸法・改行が動かないことを確認。動きあり／静止、発表、印刷も試す。ブラウザで `tests/checks/browser/deck-design-geometry.js` を実行し、枚の外へのはみ出しに加えて本文枠内の重なりも確かめる。この検査は目視の補助であり、全枚画像の確認を省く理由にしない。
6. `node bin/deck-design-check.mjs 原稿.html` とスキルの `check` を通し、既存の投稿の導線で出す。投稿後も実URLで画像欠損と代表操作を確かめる。

共通部品を直したときは `pnpm build:deck-design`。3つの見本も同じ一式に更新される。手本と構図のCSSを別々に修正して二重管理しない。

### 手元で操作まで試す

`node scripts/dev/preview-deck-design.mjs` は本番に接続せず、メモリ上の見本に対して実際の編集画面・保存処理を動かす。表示されたローカルURLで操作する。`/reset/presentation`、`/reset/proposal`、`/reset/report` で見本を切り替える。再起動すると保存内容は消える。

ブラウザでそのURLを開いたあと、`tests/checks/browser/deck-design-geometry.js` を評価すると、全12配色×5あしらいで文字・図の位置と改行を比較する。1pxを超えるずれや改行の変化があればエラーになる。縮小されたSVGの文字は再描画時の字形調整で寸法が変わることがあるため、共通部品で幾何学的な精度を指定している。

### AI-Driven Schoolの会社テーマ

会社用の新規作成では「AI-Driven School」を選ぶ。通常の基本8種類・見本94種類に共通の書体と
見出しを適用するため、学校専用の構図一覧を複製しない。編集の「スライドを追加」にある
「テーマ」からも選べ、見本の表示と保存される枚は同じ設定を使う。

書体はLINE Seed JP、見出しは濃紺から青。表紙・章扉・問いには同じ強調色を淡く混ぜた紙面を使い、
写真全面の文字は元の明暗補正を保つ。細かな表と図では既存の文字の目盛り・構図を保つ。
新しい書体と見出しは `data-deck-school` を持つ共通部品だけで扱う。旧資料では
本文を取り寄せ、対応する共通部品へ更新してから適用する。
