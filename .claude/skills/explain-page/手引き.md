
# Pages にページを作る

任意のトピックについて、前提知識がなくても理解できる HTML ページを 1 枚生成し、自分のサイト に投稿して URL を渡す。
品質基準は「入社したての新卒社会人が読んでも腹落ちする明快さ」だが、**この基準は出力には表示しない**。

**既定は「招待した人だけ」**（自分と、サイトに招待した人が Google アカウントでログインして開ける）。公開（ログインなしで誰でも読める）はユーザーが明示したときだけ。

## 2 つのモード

依頼内容から、どちらで作るかを自分で判断する。額縁・配色・品質基準は**両モード共通**で、変えない。

| | 図解中心 | 文章中心 |
| :--- | :--- | :--- |
| 使うとき | 「図解して」「仕組みを説明して」「〜とは何か」 | 「議事録を」「レポートに」「調査結果を」「手順書を」 |
| 中身の比率 | ビジュアル多め。テキストは図の補足 | 文章が主。要点や構造の箇所だけ図にする |
| 冒頭 | ヒーロー＋一枚絵サマリー | ヒーロー＋要点リスト |

文章中心でも、**ベタ書きの長文にはしない**。見出し・カード・表・箇条書きで区切り、比較や流れが出てくる箇所は図にする。

## 依存ファイル

このスキルは 3 つのファイルを読む。

- `<スキル置き場>/_shared/references/base.html` — 額縁テンプレート（Tailwind CSS CDN・Lucide Icons CDN・配色を含む）。**色の名前と、その明暗 2 組の値をここが持つ**
- `<スキル置き場>/_shared/references/デザイン規則.md` — 色・文字サイズ・線と箱の上位ルール
- `<スキル置き場>/explain-page/references/model-answer.html` — 模範回答。品質基準とデザインパターンの実例

図（順序図・状態遷移図・日程など）を入れると決めたときだけ、もう 1 つ読む。
**入れないなら開かない**（貼ると図の道具を読み込むことになる）。

- `<リポジトリ>/src/templates/mermaid.html` — 図をページに貼る一式（script 2 本と style 1 枚）。
  **色・置き方・絵記号の正本**

### スキル置き場の探し方

このスキルは、このリポジトリ（Pages の配布版）の `.claude/skills/` に入っている。
以下では、

- `<リポジトリ>` … このリポジトリの一番上のフォルダ（`bin/pages-publish.mjs` と `deployment.json` があるところ）
- `<スキル置き場>` … `<リポジトリ>/.claude/skills`（各スキルのフォルダと共通の `_shared/` が並んでいるところ）

と書く。スキルは別の仕事のフォルダからも呼ばれる（Claude Code のプラグイン、Cursor・Codex の近道）。
`<リポジトリ>` は、読んだ SKILL.md の**実体**から 3 つ上のフォルダ（`<リポジトリ>/.claude/skills/<スキル名>/SKILL.md`）。
近道越しに見えていても、近道の先で数える。最初に 1 回だけ、次で求めて確かめる。

```bash
python3 -c 'import pathlib,sys; p=pathlib.Path(sys.argv[1]).resolve().parents[3]; print(p if (p/"bin/pages-publish.mjs").is_file() and (p/".claude/skills/_shared/references/base.html").is_file() else "")' <読んだ SKILL.md のパス>
```

フォルダが 1 行出れば、それが `<リポジトリ>`。以降ずっとこれを使う。
コマンドは**いま開いているフォルダのまま**、`<リポジトリ>` を前に付けて打つ（`node <リポジトリ>/bin/pages-publish.mjs …` の形）。
作業ファイル（`page-out/` など）も、いま開いているフォルダに作る。
何も出なければ、配布物が欠けている。推測で探し回らず、そう伝えて止まる。

## ワークフロー

### Step 0: 前提確認

4 つ確認する。

**1. 額縁テンプレートがあるか** — 「スキル置き場の探し方」の手順でスキル置き場を 1 つ決める。以降の参照はすべてここを起点にする。

**2. 原本が渡されていないか確認する** — ユーザーがマークダウンやテキストのファイルを指している・長い文章をそのまま貼り付けている場合、それは「新しく書き起こす」依頼ではなく「完成した文章を体裁だけ整えて配る」依頼の可能性が高い。その場合は clean-copy に切り替えてよいかユーザーに聞く。原本があるものを、このスキルで書き直してはいけない。
ただし「議事録をまとめ直してレポートにして」のように**構成を変えて書き起こす**依頼は、原本があってもこのスキルの担当。分かれ目は「中身を変えてよいか」。

**3. 投稿の下ごしらえ** — `<スキル置き場>/_shared/references/投稿の手順.md` の「投稿の下ごしらえ（前提確認）」に従う。

**4. すでにあるページを直す依頼か** — 「あのページのここを直して」「1 節足して」「コメントを直して」のように投稿済みのページに手を入れる依頼なら、**Step 1〜4 を飛ばす**。先に読むスキルの `revise` で材料を手元に置く（文脈は `本文.md`、直すのは HTML の該当箇所だけ。`index.html` を全文読まない。`本文.md` を直して清書として出し直さない）。投稿の作法は `投稿の手順.md` の Step 5「すでにあるページを直すとき」。白紙から書き直すと、直したいのは 1 行なのに前の版にあった数字・順序・注意書きが静かに落ちる。

### Step 1: 模範回答の読み込み

`<スキル置き場>/explain-page/references/model-answer.html` を読み、以下を把握する。

- 完成品の品質水準
- デザインパターン（余白・カード・フロー図などの視覚表現）
- Tailwind CSS クラスの使い方
- Lucide Icons の使い方
- コンテンツの構成・情報量・説明の深さ

**模範回答は、情報量・説明の深さ・レイアウトの手本。** パーツ一覧やルールではなく、実物から読み取る。
ただし**配色・線と箱・文字サイズは例外**で、`デザイン規則.md` が正本。模範回答の実物とルールが食い違っていたら、ルールに従うこと。模範回答から読み取るのは、情報量・説明の深さ・レイアウトの組み立て方であって、個々のクラス指定ではない。

### Step 2: テンプレートの読み込み

`<スキル置き場>/_shared/references/base.html` を読み、額縁の構造を把握する。

- `<!-- CONTENT_START -->` 〜 `<!-- CONTENT_END -->` の差し込み位置
- `<!-- TITLE -->`、`<!-- DESCRIPTION -->` の差し込み位置
- 配色の Tailwind 設定（**本文に `dark:` を書かない**。明暗は額縁が持つ）
- 読み込み済みの CDN（Tailwind CSS・Lucide Icons）
- 額縁が持つ道具（PDF・先頭へ戻る）。**本文に書き足さない**
  - **PDF はページの頭**にあり、本文と一緒に流れていく（貼り付いていない）。滅多に押さない道具に画面の上端を恒久的に使わせないため
  - **先頭へ戻るは画面の左下**に浮いていて、しばらく下へ動かすと現れる。右下は配信側の道具の席なので空けてある
- だから**本文に貼り付く要素（`sticky` / `fixed`）を置かない**——左下と右下は埋まっていて、席を取り合って重なる
- 公開すると、PDF ボタンは**配信側の書き出しメニュー**（アイコンだけ。コピー・ファイルに保存・PDF）に置き換わる。手元で開いたときと見た目が違うのは正常。この置き換えは道具の行の中の `<button>` を消す形で起きるので、**あの行まわりの作りは触らない**（額縁の中のコメントに、そう組んである理由が書いてある）

### Step 3: ウェブで情報収集

トピックについてウェブ検索を行い、正確かつ最新の情報を集める。

身の回りの出来事（議事録・自分たちの調査結果・チーム向けの手順書など）が題材で、**手元にすでに材料が揃っている場合はこの Step を飛ばす**。外部の技術・製品・一般知識が題材のときだけ検索する。

検索は **2〜3 回** に絞る。次の観点でクエリを組み立てる。

1. **正確な定義** — 公式な定義、公式ドキュメントの説明
2. **最新動向** — 直近の変更点、いまのベストプラクティス
3. **具体例** — 実際の使われ方、たとえに使える事例

検索結果から次を整理し、Step 4 の材料にする。

- トピックの正確な定義（検索結果を優先。学習データだけに頼らない）
- 最近変わった点があれば明記する
- たとえ話に使えそうな事例や数字
- **出典 URL** — 採用した情報のソース。Step 4 でインライン出典に使う

### Step 4: コンテンツ生成

Step 3 で集めた情報をもとに本文を組み立てる。検索結果で得た定義・事実・具体例を優先する。

**書き始める前に `<スキル置き場>/_shared/references/デザイン規則.md` を必ず読む。** 色の使い方・文字サイズ・線と箱・連番・引用・本文中のコード片が入っていて、個別のパターン集より優先される。この規則と模範回答の実物が食い違っていたら、**規則のほうが正しい**。

模範回答のデザインを参考にしつつ、Tailwind の語彙で自由にレイアウトを組む。模範回答のパターンに合うものはそのまま使い、合わないものは Tailwind クラスでその場で作る。定義済みパーツに縛られない。

### Step 5 以降

Step 5 以降（ファイル作成・投稿・**手元の作業ファイルの片付け**・完了報告・ページの削除・守ること）は `<スキル置き場>/_shared/references/投稿の手順.md` に従う。

片付けを飛ばさないこと。`page-out/` は投稿するためだけに作った控えで、正本は保管庫にある。手元に残すと、次に動かしたときに前回の `index.html` と混ざる。**消さずにゴミ箱へ入れる**（すぐ戻せる状態を残す）。ユーザーが前から持っていたファイルには触らない。

片付けたあとで同じページを直すことになったら、ゴミ箱を掘り返さずに取り寄せる（Step 5「すでにあるページを直すとき」）。ゴミ箱の中は読めないし、保管庫のほうが新しい。

## コンテンツ生成の指針

- **概論 → 各論** — いきなり詳細に入らない。全体像を見せてから個別の話に入る
- **専門用語は初出で必ず解説** — 「API（Application Programming Interface＝ソフトウェア同士がやり取りするための窓口）」のように、括弧書きで平易に説明する
- **たとえ話で身近な体験に結びつける** — レストランの注文、郵便配達、信号機など、技術を知らない人でもイメージできる例を使う
- **簡潔にまとめすぎない** — 理解に必要な情報量は削らない。腹落ちするまで丁寧に説明する
- **図を早く見せる** — 見出しから最初のビジュアルまでに、テキストは最大 2 段落（各 2〜3 行）。それ以上必要なら、図を先に見せてから後ろで補足する（図 → 説明の順）。「説明してから図を見せる」より「図を見せてから説明する」方が、同じ文量でも読まされている感がなくなる。テキストで述べたたとえ話もミニビジュアル化を検討する
- **「見たことがあるもの」は説明せず見せる** — 読者がすでに体験しているもの（アプリの画面、ツールの UI、Web サイト）に言及するとき、「〜という画面が表示されます」と書く代わりに、その画面自体を Tailwind CSS で再現して配置する。読者の「見たことある」という記憶が発火する瞬間が、テキスト説明より圧倒的に理解を深める
- **ビジュアルには 2 つの役割がある** — 「構造を示す図」と「体験を再現する図」の 2 種類。どちらか一方ではなく、両方を組み合わせる。
  - **構造パターン（仕組みを頭で理解する図）** — 知識の種類に応じて選ぶ:
    - **「X とは何か」(定義)** → アナロジー図: 身近なたとえの登場人物を配置し、矢印で関係を示す。主役を中央に大きく
    - **「X はどう動くか」(プロセス)** → ステップフロー: 番号つき横並び（モバイルは縦）。各ステップにアイコン＋一言。3 枚とも同じ見た目にする。外側に面を 1 枚敷き、中の各ステップには面も枠も付けない（箱の二重を避ける）。矢印も置かない。順序は番号と左 → 右の位置で示し、ステップごとに色を変えない
    - **「X と Y の違い」(比較)** → 左右対比: 2 カラムで並べ、同じ観点を同じ行に揃える。✗/✓ の記号で差を示す。色を添えるなら `ads-positive` / `ads-negative` の 2 色を記号と見出しの文字色にだけ使う
    - **「X の具体例」(事例)** → カードグリッド: 2 列のカードにアイコン＋タイトル＋説明。カード内で「表の顔」と「裏の仕組み」を分けると深みが出る
    - **「X のすごさ」(数値)** → 数字カード: 3 カラムに大きな数字。`text-3xl font-black` と、単位・ラベルを `text-sm text-ads-muted` に落とすサイズ差で存在感を出す。数字ごとに色を変えない。3 つのうち最も訴えたい 1 つだけ `text-ads-accent` にしてよい
    - **「X の構造・中身」(階層)** → 入れ子ブロック: 外側の大きなブロック内に構成要素を配置。階層は入れ子のインデントと余白で表現する。足りなければ `bg-ads-surface` を 1 段だけ重ねる。色相は変えない
    - **「X の誤解」(訂正)** → 誤解 → 答え: **誤解そのものを見出しにする**（`text-lg font-bold` の h3 ＋ 行頭に「誤解」の無彩色チップ）。答えは見出しにせず、**本文の 1 文目に置いて太字にする**。要素は「見出し」と「段落」の 2 つだけ。「誤解:」「実際は:」のようなコロン付きラベル、✗ / ✓ の記号、カードの箱と仕切り線は使わない。**答えの側にラベルを付けない**（「正しくは」のチップを足さない）。項目どうしは `space-y-12` の余白で離す
    - **「X の変遷」(時系列)** → タイムライン: 作りは「連番の見せ方」と同じ。数字の位置に年号を置き、右にラベルと要約。縦線は引かない。時代の変化は年号と縦の位置で示し、色は使わない。「いま」に当たる 1 点だけ `text-ads-accent` にしてよい
    - **「決まったこと・やること」(議事録・レポート)** → 番号つきの決定リスト: 作りは「連番の見せ方」と同じ。担当と期限はチップで添える。未決は「未決」というラベル文字と `text-ads-muted` の薄さで分け、色相を変えない
  - **体験再現パターン（読者の「見たことある」記憶と結びつける図）** — 読者が実際に触れたことのある画面を Tailwind CSS で再現する。「あなたが見ているもの」「〜の画面では」「実際に使うとき」のような文脈が出てきたら、テキスト説明ではなくこちらを使う:
    - **チャット UI** — 吹き出し形式の対話画面。暗い背景＋ユーザー吹き出し（右寄せ）＋AI 吹き出し（左寄せ）＋入力欄モック
    - **エディタ UI** — タイトルバー（赤黄緑ボタン）＋サイドバー（ファイルツリー）＋コードペイン。AI チャットパネルを加えた 3 ペインも可
    - **ターミナル UI** — タイトルバー（赤黄緑ボタン）＋プロンプト記号＋コマンド＋出力。コードブロックとの違いはウィンドウ枠がある点
    - **ブラウザ UI** — タイトルバー（赤黄緑ボタン）＋アドレスバー＋ページ内容
    - **アプリ画面** — 上記に当てはまらないアプリ（天気予報、地図、決済画面など）。角丸カード内にアイコン＋数値＋ラベルでミニ画面を再現
    - 共通ルール: 中身はリアルすぎず要点が伝わるミニマルな内容にする。特定ブランドのロゴや名称は使わず汎用的な表現にする。Tailwind CSS クラスのみで構成する。**外側の器に `data-ads-figure="light"` か `"dark"` を付け、中は生の色で閉じる**（名前を混ぜない。理由は `デザイン規則.md` の「色の使い方」）
- **線がつながっていること自体が中身なら、手で組まずに図の文で書く** — 上の構造パターンはどれも
 「並べる」図で、順序は番号と位置が示すから Tailwind で組める。**戻る線・交わる線・3 つ以上の
 分かれ道**が出てきたら、それは並べる図ではない。手で組むと線と箱の位置合わせに時間を取られ、
 肝心の中身が痩せる。この 4 つだけは図の文（Mermaid）で書く。
  - **順序図** — 誰が誰に何を、どの順で渡したか。仕組みの説明・不具合の再現手順・申請の流れ
  - **状態遷移図** — 行って戻れる先。「ここからは戻せない」が一目で分かる
  - **流れ図** — 分かれ道が 3 つ以上あるとき。2 つまでは左右対比のほうが読みやすい
  - **日程** — 段取りと締め切り。議事録・計画のページ
  - **これ以外を置き換えない。** 3 ステップの横並び・左右対比・カードグリッド・数字カード・
   アナロジー図・ミニ UI は、上のパターンのまま手で組む。図の文のほうが手軽だからという理由で
   寄せると、ページ全体が箱と線だけの均質な図になり、アイコンも余白も効かなくなる
  - **図の中で色を指定しない。** 色は額縁の名前から自動で入る。1 つだけ目立たせたいときは
   `classDef accent stroke-width:2px` のように**太さ**で示す（`デザイン規則.md` の「色の使い方」と同じ）
  - **人は `actor`、仕組みは `participant`。** 人だけが絵記号で出る。登場するのが全部システムなら
   `actor` を使わない
  - **図に面を敷かない。** `<pre class="mermaid">` を `bg-ads-surface` の箱に入れない。
   図の箱も矢印の札の下敷きも**紙の色**なので、面の上に置くと白い四角がいくつも浮いて出る。
   手で組んだ図に面を敷いてよいのは、あちらが自前の輪郭を持たないため。**切り出しは見出しと余白で行う**
  - **状態遷移図で、戻れる先が 2 つ以上に枝分かれするときは `direction LR` と書く。**
   既定の縦だと、枝分かれの札（「絞る」「外す」…）が全部おなじ高さの 1 段に並び、
   隣り合う 2 つが**別の組**の札になって、どの矢印の札か読めなくなる（4 つのうち一番近い
   2 つが、別の組で 20px しか離れていなかった）。横に置けば、往復する 2 本の札が
   矢印の上下に分かれる。**行き止まりは「出ていく矢印が 1 本も無い箱」で示す**——
   それが状態遷移図を選ぶ理由なので、往復だけの図なら流れ図か箇条書きで足りる
  - **狭い画面のことを、図を書く前に決める。** 図は幅が足りなくても縮まず、横へ送って読ませる
   （縮めると図の中の字だけがページの目盛りから外れるため）。だから**横に伸びるほど、
   スマホで送る距離が伸びる**。登場人物は 3 人までに絞り、分かれ道の多い流れ図は
   `flowchart TB` で縦に伸ばす（`LR` で 3 方向に分かれると 700px を超える）。
   横に伸びるのが中身そのものである順序図と日程は、送って読ませてよい——
   どちらも「左から右へ時間が流れる」図なので、横へ送るのが読み方と一致する
  - **日程の `section` の名前は短くする。** 区間名は図の左に列で出て、列の幅は
   いちばん長い名前に合わせて伸びる。伸びたぶんだけ図全体が横に広がり、スマホで送る距離が
   伸びる。「下ごしらえ」「仕上げ」くらいで置き、説明は帯（作業）の名前のほうに書く
  - 貼り方（`</head>` の直前に足す一式）は `<スキル置き場>/_shared/references/投稿の手順.md` の
   「図（流れ図・順序図・状態遷移図・日程）を入れるとき」。**貼り忘れると図の文がそのまま画面に出る**
- **冒頭にヒーロー＋一枚絵サマリー**（図解中心モード） — タイトルで「何のページか」を伝えたあと、そのままトピックの核心を 1 枚の図で見せる。ヒーローの説明文を図への導入（「ひとことで言えば──」のような引き）にし、図の直後に各論への橋渡し（「ここからひとつずつ解説していきます」）を置く。ヒーロー → 一言の答え → 図 → 各論が一本の流れになること。構成:
  - **一言の答え**: 核心を 1 文で太字表示（カード冒頭）。読者が「なるほど」と思える定義を先に読ませ、そのあとの図で視覚的に裏付ける
  - **コア図解**: 一言の答えを図にしたもの。**箱は外の面 1 枚だけ**（`bg-ads-surface rounded-2xl`、枠線なし）。登場人物にはアイコンを素で置き、1 人ずつ箱に入れない。主役は絵記号を一回り大きくして色を 1 点だけ乗せ、脇役は無彩色にする。**行って戻る関係なら、一筆書きの往復路にする** — 行きは上を左から右へ矢印、帰りは下をコの字でくぐらせて左へ戻す。帰りを図の外にピルで置くと往復が読めない。矢印のラベルには `whitespace-nowrap` を当てる（列が狭いと「リクエス／ト」と割れる）。スマホ幅では縦 1 列に積み、帰りは左端の縦線で表す
  - **身近な接点**: 読者がすでに体験している具体例を 2〜4 個並べる。**アイコン＋文字を素で置き、余白で区切る**（ピルにしない。理由は `デザイン規則.md` の「線と箱の使い方」にある）
- **冒頭にヒーロー＋要点リスト**（文章中心モード） — 結論・決定事項・変更点を 3〜5 個、「連番の見せ方」の作りで先に見せてから本文に入る。1 件ずつをカードの箱に入れない。読者が冒頭だけ読んで用が足りる状態にする
- **読者のレベルに言及しない** — 「初心者向け」「入門」「未経験者でもわかる」のように読者をラベリングする表現をタイトル・見出し・本文に入れない。わかりやすさはページの品質であって読者のレベルではない
- **ヒーローバッジはトピックのカテゴリ** — タイトル上のバッジには、テクノロジー・ビジネス・開発ツール・デザイン・議事録などのカテゴリを入れる。読者のレベルを示すラベルは入れない
- **インライン出典** — 検索結果から採用した事実・定義・数字のすぐ近くに出典リンクをさりげなく添える。`text-xs text-ads-muted` で小さく薄く表示し、リンクテキストは URL そのままではなく「出典: ○○公式ドキュメント」のようにページ内容がわかる名前にする。段落末やカード下部など、視線の流れを邪魔しない位置に置く
- **日本語で** — 英語メインのトピックでも、ページは日本語で書く
- **絵文字を使わない** — OS 依存で表示が変わる。アイコンは Lucide Icons を使う
