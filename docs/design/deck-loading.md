# スライドを開く瞬間の表示

紙の幅・高さ・余白を最初から確定し、書体や図の準備で読み位置を動かさない。
見た目と実行部は、設定JSONの後・headの中へ埋め込む。既存の保存済みHTMLは、
雛形をデプロイするだけでは更新されない。

## 初回表示の順序

1. 共通のCSSを読み、紙の構図を有効にする。
2. 本文の解析が終わったら、図の原文を既存の保存関数で控える。
3. 配色・ロゴ・公開補足を準備し、紙を16:9の器へ入れる。
4. 指定された枚へ一度だけ移動する。戻る操作と利用者の入力は優先する。
5. 紙の中に動かないスケルトンを置き、指定枚の書体・画像・図を準備する。
6. 同じ位置で本文を見せ、残りの枚を準備する。

寸法の準備、閲覧の準備、編集の準備を同じ完了合図で兼用しない。

## 編集画面を開く順序

編集画面は、全枚の準備完了ではなく、**編集画面が最初に見せる枚**の準備完了で開く
（`src/lib/deck/design/typography.ts` の `whenDeckSlideReady`）。300枚の資料では残りの枚の
グラフ・図の準備に遅い端末で数秒かかり、編集できるのは一度に1枚だけだから。

- 実行部は最初の枚を描いたら `data-deck-design-live` を立て、残りを裏で描く。
  全枚を描き終えたら従来どおり `data-deck-design-ready` を立てる。
- 待たれている枚（編集画面が見せる枚・画面に入った枚・発表中の枚）は、残りより先に描く
  （`deckRenderer.whenDrawn`）。裏の描画と表示の更新は同じ順番待ちを通り、同じ枚を同時に描かない。
- 描き終わっていない枚のグラフ・図を読まない。キャンバスはその枚への押下を受け付けず
  （`deckSlideDrawn`）、段階表示の設定欄と縮小表示は全枚の準備完了を待つ。
  縮小表示は1枚ごとに資料の書体を読み込み直すため、開いた直後の操作と重ねない。
- 編集用の枠では、残りの枚は編集画面が一度画面に出てから描き始める（`deckRenderer.drawRemaining`）。
  最初の枚の画像の到着も待たない。画像の枠の大きさは決まっていて、読み手の待ち（最大1.5秒）は閲覧のためのもの。
- 枚ごとの報告を持たない実行部（独自の実行処理など）は、従来どおり全体の完了で開く。
仮表示は別の固定座標を持たず、実際の紙に置く。背景色もその枚の設定を使う。
本文の複製は作らず、準備中の操作は止め、状態通知を本文の外へ置く。

寸法変更の通知中には寸法を書き込まず、既存の次の描画タイミングへ再計算をまとめる。
初回の寸法計算と着地は同期のまま行う。編集中に器が変わっても同じ通知内で再帰しない。
編集用の画面は、準備中から閲覧用の寸法監視を停止する。編集側がサイズを決める画面で
両方の計算を走らせない。発表を開始したときだけ閲覧用の計算を再開し、終了すると止める。

本文を隠すときは透明度を使う。祖先と子に異なるvisibilityを設定して解除すると、
Chromeで画面外の枚が白いまま残ることがある。座標の検査だけでは検出できないため、
スクロール後の画像に本文が描かれていることも検査する。

## 遅延と失敗

- 書体は初回2秒まで待つ。全書体がそろうまで適用せず、時間切れ後の到着で文字を入れ替えない。
- グラフの道具は準備開始時から到着を監視し、2秒で代替表に確定する。
  最初に見る枚にグラフがなければ、その到着で閲覧を待たせない。
- 指定枚の画像は最大1.5秒。準備中の本文全体の仮表示は最大4秒で解除する。
- 裏で別の枚を描いている間も、表示済みの枚の段階操作を使える。
- 印刷には仮表示と本文を隠す指定を持ち込まない。

## 検査

```sh
pnpm verify
pnpm test:deck-loading
PAGES_TEST_BROWSER=webkit pnpm test:deck-loading
```

手元のChromeを使う場合は `PAGES_TEST_CHROME_CHANNEL=chrome`。
WebKitの実行ファイルを指定するときは `PAGES_TEST_WEBKIT_EXECUTABLE`。
画像と計測結果を残すときは `DECK_QA_OUT` にリポジトリ外の保存先を渡す。

検査では、幅1440px/390px、暗い配色、遅い書体とグラフ、待機中のスクロールと
画面幅の変更、戻る操作を再現する。仮表示と完成後の紙の位置・寸法が1px以内で一致し、
表示後に再移動せず、画面外の枚も実際に描かれることを見る。ChromeとWebKitをCIでも走らせる。

本文をheadより後から読み取る処理も、本当のbody要素をHTML解析で探す。
スクリプト中に含まれるbodyタグの文字列を本文の始まりと誤認しない。

## 既存資料の更新

最新の本文と版を取り寄せ、共通部分だけを比較して更新する。独自の実行処理は
三方比較で確認し、保存済み本文・設定・画像参照を保つ。投稿には取り寄せた完全な
版番号を指定し、競合時は取り寄せからやり直す。本文全体の再直列化は行わない。

今回の対象資料は、全9枚を幅1440px/390pxで更新前後に比較した。
本文の要素の位置と大きさは一致し、紙の内側の18枚の画像も画素単位で一致した。
紙の外縁では、周囲の机の色が反映される差だけがある。
